# Sys4AI depot memory adoption

Project identity: `sys4ai-depot`. Dataset: `sys4ai-depot-memory`.
The local principal `sys4ai-depot-director` is scoped only to this project.
The user authorized implementation of PLAN-20260904-7AEB452E and proceeding in
the current project folders with Git setup kept separate.

Canonical configuration, profile/schema references and permissions were
prepared from the verified installed consumer wheel. Their project-local
copies are now owned by the depot. The root runtime installation will be
recorded separately in `runtime-installation.json` before initialization.

Root adoption uses the shared preflight and storage implementation through the
reviewed `init preview` and digest-bound `init apply` entry. The two project
creation routes continue to use direct `init-memory` without that review step.

The initial capability is exact and lexical retrieval with canonical source
reread. Cognee/model activation is deferred; cloud fallback and network
listeners are disabled. Configuration/permissions alone are not proof of a
running service. Runtime receipts must distinguish exact readiness from
provider/model activation.

Memory is derived evidence. Execution-critical policy, Task, TRD, plan and
permission state must be reread from current canonical files. Reusable source
collections and historical/evidential records do not govern active project
files and cannot grant permission. Every independent child under `Projects/`
is excluded, whether registered or Git-initialized or neither.

Source admission is explicit: appearing on disk never registers a folder.
Reviewed later admission must record owner, relevance, path/format, namespace,
canonicality, authority, trust, sensitivity, retention and write policy. The
existing `memory.sources.register` administrative authorization boundary owns
such a change; it grants no authority to change exclusions or another project.
