# Reusable Sys4AI vocabulary sources

Version 1.0.0. These neutral definitions summarize the reusable project soul, project director, sub-agent and delivery contracts. They retain the distinction between conformance verification and fitness validation; canonical Task state, requirements documents, native goals and conversations remain separate. This file contains conceptual source material, no project instances, actor binding or execution grant.

## Project

A selected unit of work with its own identity, purpose, governing sources and change boundary. Registration describes a project; it does not grant authority over its files.

## ProjectTemplate

A reusable neutral starter from which a selected project receives explicitly adopted capability and governing assets. Existing projects do not update merely because the template changes.

## Artifact

A concrete document, file, record or other reviewable work product. Its filesystem path is a binding and may change without changing semantic identity.

## Source

Identified evidence used to support a definition or assertion. A local source reference records exact path, SHA256 and a useful locator; changed bytes must be reported.

## Specification

A governing description of required properties, constraints and interfaces. Current project specifications retain operational authority over a recalled ontology definition.

## Requirement

An explicit expected outcome or constraint with a source and observable acceptance criterion.

## Task

A canonical Sys4AI managed work record with definition of done, execution state and confirmed owner. A Task is distinct from a TRD, implementation plan, native goal and Codex conversation. Document approval does not activate a Task or establish implementation completion.

## TRD

A Task Requirement Document capturing explicit requirements and acceptance criteria. Approval settles the requirements document; it does not activate a Task, authorize implementation or prove completion.

## ImplementationPlan

A versioned mapping of requirements to implementation work, dependencies, artifacts, risks and verification evidence. Plan readiness is distinct from execution authorization and implementation completion.

## Verification

Checking that work conforms to the stated requirements, design and project contracts. Verification checks conformance; validation checks fitness for the intended use.

## Validation

Checking that the result solves the intended problem and is fit for the intended user and use. A structural check alone is not evidence of end-to-end fitness.

## Evidence

An identified observation, source or measured result supporting a claim at a stated version and verification level.

## Agent

A running or defined assistant acting within explicitly assigned scope and current instructions. A title or capability alone grants no write or execution authority.

## Role

A project-local function defined by a paired AGENTS.md and ROLE.md source, with capabilities, inputs, outputs, scope and stopping conditions. An index is navigation rather than role authority.

## Skill

A reusable instruction and tool workflow for a bounded purpose. The Skill type, an installed skill instance and the SKILL.md artifact describing it are distinct entities.

## Capability

A described ability that helps discover an appropriate skill or role. Resolving a capability does not invoke it or grant permission to execute it.

## ActionType

A vocabulary category describing an action. Modeling it does not install execution interception or pre-execution semantic gates.

## MemoryRecord

A project memory record retaining historical evidence, decisions or lessons in its own canonical store. Memory recall is evidence, not current governing authority; memory publication cannot redefine ontology semantics.

## Lesson

An evidence-backed finding about a decision, failure or verified outcome with a concrete improvement disposition. Learning and memory retain their own acceptance and publication boundaries.

## Decision

An explicit selected course or settled interpretation supported by evidence and the current authorized owner.

## OntologyConcept

A stable semantic meaning with a preferred label, definition, module ownership, lifecycle and source provenance. Concepts are not substituted with directory locations.

## Authority

The current permission to take a scoped action, established by user instructions and governing project, role, skill or confirmed Task contracts. Ontology describes authority and grants none.

## Scope

An explicit boundary of permitted inputs, outputs, artifacts, actions and stopping conditions.

## TaskManager

A real native manager with confirmed activation, execution generation, assignment and canonical writer ownership for one Task. An ordinary child is not promoted by reading root guidance.

## NativeGoal

A conversation runtime objective managed independently of canonical Sys4AI Task state. A native goal is neither a Task record nor document approval.

## CodexConversation

A user-visible Codex task, chat or conversation. Its conversation state is distinct from a canonical Sys4AI Task and does not determine the Task writer.

## ProjectDirector

The current project director coordinating authorized work, project boundaries, delegation and acceptance. A confirmed Task manager owns its assigned execution; the host retains unassigned project decisions.

## ProjectSubAgent

An ordinary native child with one bounded assignment and a stopping condition. It returns evidence and has no ungranted canonical Task, role or ontology publication authority.

## Relationship

A directed, typed assertion between stable endpoint identities, carrying a registered predicate, fact classification and source provenance.

## RelationshipType

A stable predicate definition specifying allowed source and target types, qualifiers, cardinality and whether cycles are forbidden.

## SourceBinding

A canonical connection between a semantic entity and explicitly selected current project source bytes. It never recursively imports a child project or executes a discovered skill.

## Property

A named field or characteristic in the supported local ontology profile. Unsupported JSON-LD features are rejected rather than interpreted as arbitrary semantics.

## MemoryRetrieval

The capability to retrieve permitted project memory evidence through the installed memory read and search interfaces, retaining provenance, lifecycle and source restrictions.

## OntologyRetrieval

The capability to retrieve explicit definitions, aliases and typed relationships from the selected local ontology without invoking the represented skills.

## TaskManagement

The capability to manage canonical Task execution through the current installed Task interfaces and confirmed ownership gates.

## TRDCreation

The capability to capture requirements with the explicitly selected to-trd workflow. Creating a TRD does not create or activate a Task.

## MemoryPublication

The capability to publish accepted project memory changes only through its own current exact-payload and scoped publication authority. An ontology grant is insufficient.

## OntologyPublication

The capability to publish accepted ontology changes through its separate exact-payload, current-owner and source-version gates. A memory grant is insufficient.

## TaskRequirementDocument

An initial-release compatibility spelling for the TRD concept. Use TRD as the preferred concept; this identity is retained and is never reassigned.

## Relationship vocabulary

Predicates below express directional semantic connections. Type-level connections describe a concept relationship; they do not assert execution, publication, ownership activation or filesystem changes. Instance assertions require their own current project sources.
