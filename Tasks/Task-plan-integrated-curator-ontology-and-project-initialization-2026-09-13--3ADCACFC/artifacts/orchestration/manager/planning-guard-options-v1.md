## Option A: Review a bounded supported-capacity increase

A proposed engine resource capacity of 128 MiB instead of 64 MiB retains the same complete context and target inventories, 10,000-file limit, path/symlink rules, exact source digests, owner identity and generation gates, lock-time rechecks and current backend validation. Unlike target selection changes, this does not omit any integrity coverage. It doubles the permitted aggregate read work; each _snapshot retains per-file SHA256 values and only the current raw file rather than all raw bytes. Time and largest-file memory costs still need measurement. There is no demonstrated need to change MAX_FILES, schemas, profiles, model limits or owner logic.

This is the smaller candidate if separately authorized as a tested capacity change, not an ad hoc bypass. Expected source changes: ontology_guards.py, focused test_guard_engine.py coverage and initializer assets/static-capability-v1.json; concise guard coverage/resource documentation only where existing stated bounds need updating. Active adoption: exact installed engine plus a fresh verification artifact and immutable bootstrap binding, using the unchanged adapter bindings where adapter bytes stay equal; ontology-advanced.yaml changes only its guard bootstrap reference. Exact generated setup intent/receipt names come from the supported reviewed repair. No old bootstrap or verification is rewritten.

Required evidence: reproduce the current rejection; inventory fixtures below 64 MiB, between 64 and 128 MiB, and above 128 MiB; confirm full retained file count/hash map, explicit over-limit rejection, unchanged 10,000-file rejection and no truncation; measure total evaluation time/peak memory on representative fixtures; test changed context at lock, stale engine/bootstrap, symlinks, owner/generation mismatch and unauthorized target rejection. Run the current actual-backend dispatch family matrix against the final engine, then verify selected root Task event and fresh-plan creation. Keep guard-enable/configured/semantic-pass/owner-commit evidence distinct.

## Option B: Derive narrower complete owner context and mutation targets

A durable scalable design could retain only owner-proven relevant context while preserving all cross-Task ownership and selected target coverage. Merely replacing _context's Tasks directory with canonical task.json files is insufficient: Task adapter pre/post target inventory still selects ['Tasks'], and dropping artifact coverage without owner-derived closure would weaken current guarantees. This option therefore needs coordinated ontology engine and Task/plan adapter design, trusted target derivation, catalog/new-record/recovery semantics, dependency and artifact closure, tests for omitted paths and concurrency, and exact active/generic divergence preservation. Its larger architectural scope is unsuitable as an assumed emergency repair.

## Recommendation and execution gate

Prefer evaluating Option A first if the user authorizes the bounded capacity change and measured resource tests pass. Otherwise seek a separately approved Option B design; do not narrow coverage or weaken validation as an incidental planning workaround. The existing repair preview itself calls the current bounded _context. It must be shown to run after the host's authorized relocation of only newly produced incidental diagnostics, with enough margin to complete repair; if it still cannot run, stop for a supported bootstrap-recovery design rather than directly patching installed code.

The planning manager owns no guard, source, Template or shared memory writes. The host must resolve actual overlap through the guard author's current-owner checks before any adoption; historical manager absence alone is not permission. After any authorized repair, reopen exact current state and retry only the original uncommitted planning event. Then perform the full independent planning team and deliver the managed draft.
