## Broker and exact owner operations

The broker owns the App Server stdio transport, private prior-authority store, exact operation grants and frozen executable/import/config closure. Trusted code and every dynamically loaded project-installed Task/role/guard helper must be outside candidate read/write scopes, pinned by hashes and reopened before dispatch. Use isolated Python startup, verified explicit module paths, fixed trusted cwd, minimal environment, absolute resolved executables and closed inherited descriptors. No candidate cwd, PATH/PYTHONPATH, startup hook, supplied import/config path or proposed executable enters this process. Do not pass candidate-controlled code into owner helpers.

Only a genuine server-origin item/tool/call on the broker's protected live connection constructs VerifiedCallContext. It binds session, request id, callId, threadId, turnId, selected tool, observation sequence and raw-frame digest. Candidate arguments contain operation data, operation_id, proposal/artifact reference, exact payload digest and expected source/owner versions. Reject actor, issuer, grant contents, effective policy, authentication flag, environment, import, executable, profile, raw protocol and shell fields. The server envelope identifies the caller; expected generation in proposal data is a precondition and cannot override the current canonical generation.

The concrete entry is dispatch_verified(context, request). Context is a nonserializable process-scoped value installed only by protected transport code and available to the owner authorizers during that invocation. Serialized evidence/grants and actor strings cannot create it. New owner grants passed through an ordinary CLI without a current verified context fail. This mechanism depends on actual process/OS isolation; a Python object or same-user process by itself does not prove security.

Expose a closed union: policy.inspect; target.classify; artifact.submit; artifact.read; task.create; task.event; task.response; memory.publish; memory.recover; ontology.publish; ontology.recover; and fixed runtime observe/message/followup/interrupt/resume operations over already bound actors. Map every event to the existing Task owner's closed event union. No generic write_file, function-name dispatch, arbitrary argv, task command, process/spawn, thread/shellCommand or raw transport proxy is exposed. Runtime methods are concrete inspected adapter methods, never candidate-supplied JSON-RPC names. Unsupported owner operations hold. Bootstrap task.create and manager reservation/receipt/activation have a bounded prior grant; after writer transfer controller Task mutation fails. Ordinary workers cannot request canonical publication. Manager publication remains allowed through its exact authenticated owner route, not direct storage writes.

Curator grant-v1 binds issuer/prior authority, one-use nonce, issue/expiry, actual native actor/session, controller and charter, project/repository/canonical root/branch, policy edition/hash, classification hash, source snapshot/files, payload digest, operation class, bounded paths/tools/network/budget, Task/execution/generation/writer, owner state, current native observation and trusted code/profile manifest. Private authority/credentials remain outside all candidate roots; candidates receive opaque handles and redacted results. Memory/ontology grants are separate, short-lived owner-specific envelopes and preserve their existing maximum freshness requirements.

Dispatch order is authenticate, validate request/bounds, reopen current owner/policy/source/map, classify complete targets, issue and check exact independent owner grant, call the existing owner, collect the actual receipt/post-state and consume the private grant. Preserve the owner's lock-time and per-write rechecks. Serialize by canonical project/branch coordination root; unresolved clone or remote ownership holds. Never nest different owner locks or claim cross-owner atomicity. Delivery states issued/dispatching/owner-partial/consumed describe transport only. Duplicate calls are rejected; successful operation retry returns the original receipt only after matching its post-state. Partial or uncertain publication reconciles its original owner journal and payload, with fresh exact recovery authority. Later edits block blind replay. No new operation ID conceals partial work.
