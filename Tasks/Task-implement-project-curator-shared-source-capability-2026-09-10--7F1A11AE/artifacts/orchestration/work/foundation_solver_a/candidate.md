## Direct interface findings

1. `orchestration_state.py` currently requires orchestration `version == 1` and fixed `FIELDS`, `ASSIGN_FIELDS` and `EVENT_KEYS`. `native_id` accepts canonical slash paths only. `receipt` accepts only actual collaboration spawn/list shapes; `apply` currently establishes child ancestry with a slash-prefix check. The source explicitly says receipts are cooperative evidence, not OS authentication. App Server IDs cannot safely be enabled by relaxing that regular expression alone.
2. `memory_publish.authorize(root, config, grant_file, operation, payload_sha256, actor, *, paths, now=None)` accepts a strict v1 grant and actual collaboration roster. It reopens current configuration, exact Task hash, generation, manager assignment, writer, role reads and launch receipt. `memory_recovery.transact` calls authorization before and inside the existing lock and again during each write; journals retain grant path/hash and original/committed bytes. Preserve these checks and recovery ownership.
3. `memory_evidence.installed_helper` and `ontology_authority.read_task` dynamically import the selected project's installed Task/role helper code. `orchestration_state.role` imports the installed role catalog. Memory and ontology guarded operations can load `ontology_guards.py` according to project configuration. Freezing only the top-level Curator script is insufficient: all transitive helper/import/config paths must be protected and bound to approved hashes before executing them.
4. `ontology_authority.authorize(project, grant, proposal, preview_sha256, *, now=None)` accepts strict ontology grants v1/v2, with v2 carrying `advanced_config_sha256` and `proposal_review`. It validates independently scoped ontology authority and current managers, including overlapping other managers. `ontology_publication.publish(root, proposal, grant, *, expected_preview_sha256, fail_at=None)` owns its locked publication and exact accepted intent. No alternate Curator publisher is needed.
5. The supplied experimental schema advertises `InitializeCapabilities.experimentalApi`, `ThreadStartParams.dynamicTools` and `permissions`, and `TurnStartParams.permissions`; each named permissions field is mutually exclusive with the legacy sandbox field. `ThreadStartResponse` reports model, nullable reasoningEffort, instructionSources and activePermissionProfile. Its legacy SandboxPolicy has no restricted-read shape. The active profile response names the profile, not the complete resolved rule set, so it cannot alone prove enforcement.
6. The real dynamic request shape is server-initiated `item/tool/call` with request `id` and params `{arguments, callId, threadId, tool, turnId, namespace?}`. Identity comes from these server params on the protected connection, never `arguments.actor`, an operation ID, a returned filename or JSON submitted by a candidate.
7. The installed ThreadItem discriminator is `collabAgentToolCall`. Its required fields include id, senderThreadId, receiverThreadIds, agentsStates, status and tool. Tool enums are `spawnAgent`, `sendInput`, `resumeAgent`, `wait`, `closeAgent`; item states are `inProgress`, `completed`, `failed`. Agent states include pendingInit, running, interrupted, completed, errored, shutdown, notFound. Fields `model` and `reasoningEffort` describe requested settings, not effective settings.
8. Thread objects expose actual `id`, `sessionId`, optional `parentThreadId`, optional `forkedFromId` and structured `source`; native subagent `source` can contain `thread_spawn.parent_thread_id` and depth. `threadSource` is a client-supplied analytics label and must never establish parentage. `turn/completed` describes a turn; it cannot by itself prove permanent actor shutdown or revoke a logical writer.

The copied schemas are sufficient to design parsers. They do not establish that dynamic tools propagate to native children, that a child can receive an enforced distinct permissions profile before its work turn, or that current effective model/effort and stopping can be obtained for every child. Those are mandatory native proof questions.

## Policy and classification interfaces

`curator_policy.py` owns strict JSON-compatible YAML decoding, rejecting duplicate keys, booleans in integer fields, unknown keys/versions, control characters and unbounded structures. Public pure functions: `load_policy(path)`, `validate_policy(document, observation)` and `evaluate_operation(policy, accepted_entitlement, operation, observation)`. They return a structured decision with `state`, `code`, `missing`, `observed_bindings` and `allowed`; no operation creates files, Tasks, grants or native calls.

The v1 configuration schema explicitly distinguishes capability configuration from accepted authority. Required sections: module version; project `{id, repository_id, coordination_root}`; branches; selected controller/charter reference; schedule `{enabled, debounce_seconds, catch_up_seconds, dependency_cadence_seconds}`; bounds `{model_calls, work_seconds, candidate_bytes, concurrent_agents}`; independent operation selections; trusted source/tool/network selectors; notification selection; runtime selector; accepted-policy reference. Neutral values are null project/repository/root/charter/runtime selectors, empty branches/entitlements/destinations, disabled schedule and autonomous writes, zero work/model bounds and no service/hook state that implies installation. Domain specialization supplies capability descriptions only. Configuration references to an accepted entitlement are inert unless the private issuer store confirms its exact digest, destination, authority receipt and current validity.

Independently selectable operation classes cover bounded analysis, data/documentation, technical maintenance, protected governance, filesystem read/write, canonical memory/ontology publication, capability adoption, trusted package-source access, runtime package/model installation, network, external tools, service/hook installation, commit, local integration, push, merge, destructive action, cross-project action and external notification. Support means each is representable and denied unless selected; it does not mean foundation code implements all later-phase operations. Unsupported dispatch is a precise hold. Treat malformed configuration as blocked; a missing selected runtime/root/volume as unavailable; absent required authority as blocked. A neutral capability can report installed/inactive with an explicit missing-selection list and must never report operational readiness.

`curator_classification.py` exposes `classify_target(trusted_map, target_identity, proposed_ranges, snapshot)`. The protected v1 ownership map records stable content ID, exact path or explicitly declared pattern, file class, section anchors and expected anchor digest, canonical sources, owning helper/generator, protected sections and affected interfaces. Use full file/section coverage, not only filename extension. AGENTS/charters/roles/skills/config/schema/validators/the map itself are governance; README descriptive sections are documentation but operational instruction sections are governance; ONTOLOGY/WIKI is derived and routes to the ontology generator; completed Task responses are historical and route to the Task owner correction mechanism. Explicit narrow declarations resolve broad defaults, but no override can lower the protected governance floor of its own map or approving code. Unknown owner, duplicate stable ID, missing section anchor, conflicting overlap or mixed-class patch uses the stricter valid route or holds. Rename alone cannot change content class. Resolve filesystem identity before classification; reject case/Unicode collisions, links and ambiguous aliases rather than assuming string equality means identity.

## Authenticated broker transaction

`curator_broker.py` is a trusted process with a fixed executable and frozen import closure, protected private storage and a private App Server stdin/stdout connection. Candidate actors have no broker socket, credential, private grant, writable import root or raw protocol method. Start trusted Python with isolated imports (`-I` plus explicit verified module paths), fixed cwd outside candidates, a minimal environment and close-on-exec transport descriptors. Do not use candidate cwd, PYTHONPATH, PATH executables, startup hooks, arbitrary config/module paths or shell strings. Recheck all executable/config/helper digests before a transaction. For existing helpers that read project `.agents` paths, those paths are a broker-controlled read-only installed edition outside every candidate read/write profile and are included in the frozen manifest; freeze ontology guard configuration and its entire selected loader closure as well. Missing transitive bindings hold execution.

Expose a finite dynamic tool vocabulary: read-only scoped observations; manager reservation; exact Task event/response; candidate artifact submission; exact memory operation; exact ontology publication/recovery. The broker owns dynamic tool input schemas and validates them again. Arguments carry only proposal/operation data, expected versions and stable operation IDs. The decoder rejects actor, issuer, effective policy, trust-context, protocol, executable, import, shell and credential fields. A broker-owned envelope records transport session, actual request id, callId, threadId, turnId, selected dynamic tool and raw-frame hash. The transport reader creates a non-serializable verified call context only after checking that the request belongs to the current live session, active turn and reserved/activated actor. A JSON field saying `authenticated: true` is never such a context.

The concrete dispatch entry is `dispatch_verified(context, request)`; no CLI or dynamic tool can manufacture `context`. It binds the request to the current policy, current Task execution/generation/writer, accepted exact operation, selected scope and source/payload versions. Calling the ordinary owner CLI with an actor string remains insufficient for new Curator envelopes: owner v2/v3 authorization requires a broker-only verified context in addition to the serialized grant. Deliver this context using a scoped in-process context established only inside the frozen broker/owner process; never serialize it into candidate arguments or accept it from ambient environment variables. Its own trust is conditional on OS denial of candidate code execution/import/write inside that process. Owner functions continue to validate current canonical files at each existing recheck, so the context cannot preserve stale authorization through a concurrent change.

A v1 Curator exact-operation grant binds issuer ID/authority receipt, nonce and issue/expiry, transport session and actual native actor, selected controller/charter, project/repository/canonical root/branch, accepted policy edition/hash, source snapshot/files, exact canonical payload digest, operation class, bounded read/write paths/tools/budget, owner name, owner Task/execution/generation/current writer and expected owner state. Issuance reads prior accepted authority, never proposed policy. Grants and credentials stay in private protected storage; a candidate receives only an opaque operation handle and redacted result. An accepted standing entitlement may cause automatic issue of this fresh operation grant without another human prompt.

For each request: (1) authenticate server envelope; (2) reject unknown tools/fields and check bounds; (3) reopen exact operation, accepted policy, source snapshot, ownership map and current manager; (4) classify all targets; (5) issue/check independent owner-specific grant; (6) execute only the registered existing owner operation; (7) capture the actual owner receipt and exact post-state; (8) mark the private one-use grant consumed. Under the owner's existing lock, source/payload/scope/manager checks run again. Serialize by logical project/branch canonical coordination root; refuse unsupported clone/remote ownership. Never hold one owner lock while acquiring another owner's lock. Do not claim a cross-owner atomic transaction.

The request journal is transport/idempotency evidence only. States may be issued, dispatching, owner-partial or consumed; these are not Task lifecycle states. Duplicate callId/request ID is rejected. An exact operation replay after successful publication returns its prior result only after confirming current owner post-state; it performs no new mutation. If the broker crashes after an owner committed, inspect that owner's journal under the original operation ID before deciding the next step. An in-flight or partially committed request never receives a second operation ID or blind relaunch. Recovery needs its own fresh operation-specific owner authorization and retains the original payload. A later human edit blocks replay. Revocation stops future grants and cannot erase accepted owner history.

Typed owner routes are `task_state`'s existing orchestrate/response transaction, `memory_publish.publish` (and existing memory recovery), and `ontology_publication.publish/recover`. Scope includes required owner journals/response/projection writes; those paths are derived by each owner, never expanded by a candidate. Do not expose a generic `write_file`, arbitrary `task command`, subprocess/exec, arbitrary function name, `process/spawn`, `thread/shellCommand` or raw App Server proxy. Governance proposals may change future selected governance through separately scoped publication; they cannot modify the current broker, enforcement or accepted-policy bytes. Such broker upgrades are out of band and outside this execution.

## Compatible owner extensions

### Task

Keep Task schema 1 and schema 2/orchestration-v1 parsing, bytes and behavior unchanged. Add explicit orchestration-v2 for newly selected Curator executions. The default remains v1 for existing Director use. `task_state.new` receives a strict optional `orchestration_version: 2` only when orchestration is enabled; absence retains current behavior. Do not silently convert existing records or reuse a v1 execution as v2. Existing completed history can remain history; a new selected Task can use v2. A future conversion route would need separate explicit exact-source preservation and is unnecessary for this release.

Orchestration-v2 retains the same lifecycle, assignments, categories and transaction owner but adds strict `controller_origin` and `native_protocol` fields. `controller_origin` has its own version and binds controller kind/id, selected charter `{path, sha256}`, accepted policy reference, frozen execution input/snapshot references, project identity and canonical coordination root. Reading a charter creates none of this state. `native_protocol` binds the selected provider/envelope version/session/schema/runtime hashes. Version dispatch applies to all event actor/assignment IDs, observations, histories, receipt checks and recovery paths, not merely launch. Unknown fields remain errors in each version.

Add `native_observations.py` as the Task owner's strict observation parser. It can validate an App Server envelope containing provider/version, observation kind, session, subject/parent thread IDs, turn/item/request locators and authentic observation-file hash. For collaboration-v1 keep existing canonical slash IDs and ancestry checks. For App Server retain actual raw thread IDs; ancestry requires the completed native spawn item AND the observed child parentThreadId/source relationship in the same session. Reject client-supplied `threadSource` as authority. A fresh broker verification authenticates a file's origin; a content hash by itself is only an integrity check.

`manager.reserve` records exactly one logical manager before native launch; the real observed native spawn maps the reservation to one actual child. Receipt mismatches, extra receivers, changed parent/session or repeated launch cannot activate it. `manager.activate` requires exact role and charter read hashes and observed settings/context. Activation switches the sole canonical writer from bootstrap to that manager. The trusted broker mechanically writes on behalf of that logical writer; it is not another manager. After transfer, bootstrap mutation is denied except already-defined exact recovery controls. Every ordinary worker publication request fails the current-writer check. Manager replacement requires actual old-owner reconciliation and the original explicit recovery authority. No timeout or missing roster entry proves stopping.

Preserve generic/complex/extra-complex gates, candidate invalidation, reviewer mapping and distinct implementers. Version-aware native adapter metadata must also cover assignment.inputs message/follow-up receipts and conflict delivery receipts; leaving those collaboration-only would break recovery despite a passing launch test. Keep read-only/status/no-op routes free of Task creation and retain generic explicit Task selection without depot age closure.

## Native adapter and confinement

`curator_runtime.py` defines typed adapter results and explicit readiness states. `curator_runtime_codex.py` owns JSON-RPC request correlation, initialize/initialized, selected thread/turn operations, notifications, dynamic requests, replay rejection and durable observation locators. Start only the configured frozen binary via an argument vector. Negotiation uses the copied schema version and experimentalApi when named profiles/dynamic tools are selected. Reject unsupported fields and a response profile/model different from the selected values. No idle policy validation starts the runtime.

Top-level controller startup is broker-owned thread/start. Native manager and worker identities must originate in actual native spawnAgent items. Creating unrelated thread/start sessions with a role name is not proof of native children. Map observations explicitly: spawnAgent to launch; sendInput/resumeAgent to message/follow-up; fresh thread/read plus authenticated active requests/collab observations to supervision; native closeAgent and turn/interrupt with observed resulting states to stopping. Preserve raw statuses: pendingInit, notFound, shutdown and a completed turn are not silently equivalent to confirmed stopped. Keep native status and Task accepted/completed status separate. Reconnect uses the known session/thread/operation and reconciles observations before new work. An uncertain spawn keeps its reservation.

Use a staged read-only bootstrap to avoid an unconfined first child turn. Controller/manager initial profile permits only selected frozen inputs and native coordination; private stores/canonical files/sibling artifacts are denied. A native child's first turn receives only exact roles and frozen inputs under that inherited restrictive profile. It proves role readiness without candidate mutation. Before the work turn, the trusted adapter selects that actual child's own named permissions profile, with read access to the shared frozen problem and write access only to its candidate directory, and verifies current effective selection. The required ability to apply and enforce this profile before the work turn must be demonstrated; otherwise hold that work mode. Do not assume inheritance of a parent profile that can read all candidate directories proves solver independence.

An alternative within the same design for pure solvers is no direct candidate file access: candidates submit artifacts through an authenticated narrow tool, and the broker writes only their assigned artifact path. Their filesystem profile still excludes every sibling output. This tool never reads or returns another solver's draft. It is an artifact transport, not a canonical publisher. Workers requiring process/file tools receive their own observed scoped profile. Select one proven route per category and record it; do not mix unproved mechanisms in a pass claim.

The broker withholds sibling candidate content from the manager until all initial solvers have dispatched. Solvers receive byte-identical whole-problem packets and independent input histories. Actual candidate directories have no hardlinks/shared mutable aliases and no common readable output directory. The parent only receives path/hash/status while later initial solver contexts are being prepared. After the dispatch barrier, reviewers get exactly their assigned candidate, the senior gets every current passed candidate/review and the implementer gets the exact accepted synthesis. Native context tests try to retrieve unique sibling canaries as well as checking packet hashes and actual effective permissions.

Pin effective controller model/effort from observed resolved settings. For each child require observed equality or an explicit runtime inheritance guarantee that covers child custom-role overrides; requested spawn item fields alone are insufficient. Capacity is observed and bounded; the full team remains queued when slots are absent. Native built-in spawning can happen before client-side monitoring reacts, so a client counter is not a proven hard model/agent budget. Pin and verify the runtime's supported capacity/budget enforcement, or report the tighter bound unavailable. Never promise an exact hard token ceiling that the selected runtime cannot enforce.

`curator_confinement.py` derives only a deny-by-default host profile from the accepted manifest. Resolve `/var` versus `/private/var`, interpreter symlinks and framework paths before profile construction. Allow only necessary system/interpreter reads and each selected source/work path. Deny broker/issuer code and runtime private storage, all canonical Task/memory/ontology/role/setup ledgers and control records, grants, credentials, unrelated projects, sibling artifacts and unselected network/tool routes. Do not allow the project root merely because the candidate lives beneath it. The actual App Server can use its separately selected provider authentication/network path; candidate processes cannot read it or use that network entitlement. Descriptor inheritance and child processes must remain confined.

At trust boundaries use lstat/realpath, exact directory-entry spelling, normalized collision detection, no-follow regular-file opens and inode checks; reject unsafe symlinks and hardlinked files for candidate/owned targets. Check identity again immediately before mutation. Lexical path prefix checks alone are inadequate. Test actual aliases on the host, including case-sensitive fixtures where needed. A malicious branch/diff/note is JSON/argument data, never formatted shell. Native proof pairs an allowed write with each blocked protected action and reopens final canary/canonical inventories.

Pause first latches no-new-dispatch and revokes future issue eligibility, then requests real interruption and inspects known writers and partial owner journals. No replacement manager or resumed publication is authorized until reconciliation. Diagnostic records distinguish not_run, blocked, unavailable, failed and passed. Hash changes to adapter, policy, broker, owner code, profile or relevant runtime invalidate the affected native proof at release.
