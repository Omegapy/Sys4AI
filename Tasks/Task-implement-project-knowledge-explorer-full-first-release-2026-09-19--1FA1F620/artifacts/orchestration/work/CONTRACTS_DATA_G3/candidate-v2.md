## Configuration contract

`ontology-explorer.yaml` is optional strict UTF-8 JSON, the repository's supported YAML subset. Reject duplicate keys, NaN, booleans where integers are required, unknown fields, excessive depth/size, and wrong project identity. Missing configuration means valid safe defaults selected from canonical project identity; it is not permission to read another directory. Present-but-invalid configuration blocks new reads. Configuration itself cannot supply file roots, authority, code, markup, arbitrary links, executable hooks, or additional source allowlists.

Exact top-level shape:

```json
{
  "schema_version": 1,
  "project_id": "the-canonical-project-id",
  "presentation_version": 1,
  "starting_ids": [],
  "categories": [],
  "predicate_labels": [],
  "process_views": [],
  "limits": {}
}
```

Only `schema_version` and `project_id` are required; omitted remaining keys take the displayed defaults. The neutral starter uses `project_id: null` with empty mappings and no runtime activation. Null is valid for starter inspection only; active launch requires normal canonical specialization and matching `project_id`. Name/purpose come from canonical configuration, not this file.

Each category is `{id,label,type_ids,entry_ids}`: ASCII category key up to 40 characters, plain label up to 80, unique exact canonical type IDs and entry IDs, at least one selector. Membership is the union of exact declared `@type` matches and exact IDs, intersected with reading visibility. It is a presentation grouping, never an inferred type/hierarchy. Default categories are All and supported explicit canonical type categories, named from their canonical labels. The implicit `all` category has empty selector arrays and denotes all otherwise visible reading records; explicit configuration cannot reuse its reserved ID. Do not guess Skills, Roles, or Processes from label substrings. Empty configured groups may appear with an honest empty explanation; unsupported auto-derived groups do not appear. At most 32 categories including all, 32 selectors total per category, and 12 starting IDs. Every reference must resolve in the same validated snapshot; wrong kinds or unresolved configuration IDs block configuration rather than invent labels.

`predicate_labels` items are `{predicate_id,forward,inverse}` with exact predicate identity and plain reviewed phrases up to 120 characters. `inverse` is string or null. Without a reviewed inverse, incoming reading retains subject-predicate-object sentence order. Friendly labels cannot strengthen `relatedTo` into causality/dependency. This map changes presentation only; predicate definition, ID, qualifiers and direction remain available.

`process_views` items are `{id,field_relations,ordered_source}`. `id` is an exact canonical identity. `field_relations` is an object with optional keys `applicability`, `roles`, `inputs`, `outputs`, `related_skills`, `related_documents`, `prerequisites`; each contains up to eight `{predicate_id,direction}` selectors. There is no arbitrary field-content string. `ordered_source` is null or `{owner_id,reference_id}` selecting an already bound source reference from that process or one of its authorized bindings. At most 64 explicit process entries. Purpose uses the record's definition; scope uses its recorded scope note. Each displayed derived field carries its supporting relation IDs. Mapping provenance belongs in the reviewed adoption/change decision, and the mapping digest belongs in the snapshot.

`limits` permits only these lowerable keys: `page_items`, `response_bytes`, `request_bytes`, `request_seconds`, `source_excerpt_bytes`, `initial_nodes`, `initial_edges`, `display_nodes`, `display_edges`, `snapshot_bytes`, `selected_input_bytes`, `selected_files`, `source_files`, `records`, `relationships`, `journal_files`, `journal_bytes`, `sessions`, `session_seconds`, `cursor_seconds`. Values must fit the bounds below; an invalid value is rejected, never silently raised. Effective map initial limits also take the minimum of initial/display/API/canonical limits. No browser request changes these server limits.

## Transaction coordination and immutable snapshots

An immutable view is a validated `Project` plus compact indexes and the complete selected manifest. It is derived and memory-only, not a new canonical store. Preserve normal `load_project(validate=True)` semantics; never use `validate=False` to make a graph appear usable. Missing-reference validation errors block current reads with precise safe error codes; broken data must not be given invented labels. Current records already validated by the loader can be shown with stale/unavailable source warnings.

1. Resolve the caller-selected root once at startup, reject symlink aliases, and retain its device/inode identity. The browser never selects it. Before materialization or revalidation, open every relevant directory/file through the existing no-follow descriptor pattern. Track absent optional files as explicit absent markers, including `project.json`, the root registry identity observation, and `ontology-explorer.yaml`; appearance is a change.
2. Observe `control_records/ontology/publication.lock` without creating directories or files. If present, open O_RDONLY/O_NOFOLLOW, require regular single-link identity, acquire `LOCK_SH | LOCK_NB` on that existing descriptor, and retain it across journal inspection, materialization, and postcheck. This coordinates with the existing exclusive publisher lock; it introduces no second writer lock path. If busy, retry within the bound or return `knowledge_updating`. Confirm the path still names that inode at the end. Never call `operation_lock` or create a replacement lock.
3. If the lock is absent, capture the nearest existing parent-directory identities and absence explicitly; materialize with before/after journal inventories and selected-byte manifests. Recheck the entire absent-path chain and the lock at the end. If a lock or directory appears, disappears or changes identity, discard and retry using the now-existing lock. A completed supported publication leaves the lock file present, so missing-to-present is observable. If coordination cannot be established because of unreadable/unsafe paths, malformed state, unsupported platform, or journal bounds, fail closed. Do not convert uncertainty to 'no writer'.
4. Read bounded `intents`, `receipts`, and `recovery` inventories using descriptor-relative no-follow reads. Validate operation IDs, supported shapes, intent digest, proposal payload digest, preview digest, prior-content digest bindings, exact target set, and receipt-to-intent/payload/preview identity. This is pure validation, not `_candidate`, `preview`, `publish`, `recover`, advanced validation, or current grant checking. Handle an unreadable/malformed item's unknown targets conservatively as affecting the selected read.
5. A selected-affecting intent without a matching valid complete receipt is unresolved even when canonical bytes are stable, every change currently equals its target, or recovery is absent. A partial recovery without valid matching completion remains unresolved. A valid complete matching receipt supersedes its matching old partial recovery record, which the current writer deliberately retains. Completion requires one committed file record for every proposal change, with matching paths/before/after hashes. Never require every historical complete receipt's after bytes to equal today's files; later valid publications legitimately supersede them. Orphan/mismatched receipts or recovery records do not establish completion. An unresolved operation is relevant when it changes any selected canonical/module/source/config input, or changes configuration capable of selecting those inputs. Uncertain scope fails closed; a proved disjoint historical operation can be excluded with internal evidence.
6. Under that coordination observation, build the canonical view and compare the complete before/after manifests. Include canonical config/context/module manifests/locked module file set/project and binding files/competency inputs, every actual selected source hash or explicit unavailable marker, exact core/helper digests, adapter/schema digests, identity files consulted by the canonical loader, and presentation bytes or absent marker. Also recheck discovered file sets so additions cannot evade digest checks. Do not rely on mtimes. Source-unavailable state must be stable across the observation; transitions retry.
7. Compute the snapshot ID as lowercase SHA256 of canonical serialization of `{schema:1, root_identity_digest, project_id, code_epoch, canonical_context, additional_inputs, adapter_version, presentation_sha256}`. Timestamps are metadata only. The root digest is based on resolved path and device/inode; it is not a browser-supplied identity. The complete manifest stays server-side; responses carry only necessary compact identity/version metadata.
8. Every newly requested current read repeats bounded current-input/coordination validation before using cache. A cached digest match permits index reuse, not skipping byte checks based only on mtime. Changes to selected source observations, canonical data or valid presentation/configuration mappings create a new validated candidate snapshot; they cannot mutate the existing object. Executing helper/adapter/schema/build changes instead trigger the sticky code-epoch drift rule below and never create a new snapshot in the old process. Swap current only after validation succeeds. Existing screens may retain their old snapshot with a visible warning. New data for an old expected snapshot gets `snapshot_changed` rather than mixing records.

Cache keys contain resolved root identity, project ID, snapshot digest, pinned code epoch, helper/adapter version and presentation digest. There is no global cross-project cache. The session does not pin history indefinitely. Transient source bytes are discarded after hashing or bounded extraction.

## Startup code epoch and drift (DATA-R4)

Include the selected interpreter implementation/version in the epoch. Reject unexpected, symlinked, missing or mismatched members. Compute `code_epoch = SHA256(canonical_bytes(execution_manifest))`; retain the manifest and exact helper digest map in memory. Source/ontology/configuration/presentation inputs are separately classified as reloadable data. A file selected as both source evidence and executable code is executable for drift handling.

The executing closure must identify the actual source bytes loaded, not a rehash of filenames after import. The implementation must start the dedicated service/worker from a clean verified closure, load project-owned Python modules from those exact verified source bytes (compile those bytes through the fixed source loader, with no project `.pyc` reuse or ambient imports), and retain each loaded-byte digest. The supervisor/worker handshake compares the expected manifest/epoch and loaded closure before accepting a session. Already-imported modules of unknown byte provenance are ineligible. Standard-library/interpreter components remain the selected trusted runtime; no canonical document is importable as code. Before and after initial load, recheck the installed package manifest/file set. Drift aborts startup without publishing a usable service session. This is a required implementation invariant, not a claim that the proposed loader exists.

Before every session/read/asset response and before publishing a new snapshot, validate installed executing-code/schema/build bytes and their file sets against the pinned startup manifest. Revoke sessions/cursors, cancel pending reads, terminate/reap the owned worker and stop serving knowledge/assets. Do not automatically restart into new code, silently hot-reload, reinterpret existing cursors, or issue a new knowledge snapshot. The minimal public health identity may report `package_changed`; its response includes no project data. Host/Origin checks still precede disclosure. A later restoration of old bytes does not clear the sticky state.

The browser retains old readable context and desired route, marks it unavailable for current reads, clears credentials/cursors and asks for explicit fresh local reopening. The launcher must verify a complete new package and start a new service instance and fresh session. No old bootstrap/session/cursor survives. Every read request/response carries the pinned `code_epoch`. A late response from another epoch is never applied as data.

Only same-epoch ontology, source-observation and valid presentation changes may use Refresh knowledge. These still require the existing transaction/digest/snapshot rules. A worker resource failure may be recovered by at most one later explicit read/reconnect under the same verified epoch, with new worker loaded-byte verification; code drift never uses that recovery. Fresh startup and old-client rejection are distinct test cases.

## Closed wire and scalar definitions (DATA-R1, DATA-R2)

The following notation is normative for schema generation. Objects have exactly the listed keys, all required unless a configuration default is explicitly stated. Additional keys are rejected. A union means exactly one listed shape selected by its discriminant; it does not permit mixing branch fields. `T|null` is the only nullable notation. Arrays are JSON arrays, preserve order unless normalization is explicitly required, and satisfy both their stated count and complete-envelope byte budget. Integers are safe JSON integers; booleans and floats are not integers. JSON uses strict UTF-8 with duplicate-key/non-finite-number rejection and depth at most 16. Bounded source/canonical JSON rendered as text is not decoded into an executable object.

## Oversized-item progression (DATA-R3)

The serializer measures compact UTF-8 bytes of the complete final envelope, including coverage and the actual signed next cursor, before sending. A logical result is either one complete Summary/Edge or one Marker for exactly that identity. page.returned counts both; coverage returned_edges counts only complete Edge values. A marker keeps coverage.complete false, adds item_omitted plus its byte_limit/field_limit reason, displays the exact identity and Open detail action, and is retained visibly when the client appends pages. It does not imply the corresponding statement has been read/rendered completely.

There are three distinct cases:

1. **Deferred only by the remaining page space:** The next complete item fits an otherwise empty legal page under the same scope/limits but not the partially filled current page. Finish the current page. Do not return a marker and do not consume the deferred item's key. next_cursor points after the last actually returned complete item/marker. If bounded lookahead proved the deferred item exists, has_more=true. The next page returns it normally.
2. **Full item cannot fit even an empty legal page:** If a complete item violates a fixed compact-field bound or exceeds a fully empty envelope with the actual needed cursor, construct Marker. If Marker fits, return it as the logical result, consume precisely that item's full stable ranking/relation key, and allow next_cursor to advance past it. Continue to later fitting items within the page count/byte/work bounds. Detail reading uses the named lossless entry section; graph clients never fabricate an edge from a marker. Omission is explicit, not a skipped identity.
3. **Even the marker cannot fit:** If the current page already has logical results, finish that page without consuming this item's key; its next cursor stays after the last returned result and has_more=true when proved. The subsequent empty-page attempt returns resource_limit, returned=0, next_cursor=null and no identity skipped. If no result could be emitted initially, return that bounded error immediately. The request is not retried automatically; the UI offers narrower reading/detail if the selected ID is already known, or the external documented limit-maintenance route. Retrying identical bounds is not described as progress. If a signed cursor alone makes the minimum envelope too large, use the same rule; never omit required scope or weaken its MAC to manufacture a page.

Entry/source text chunks and process text fragments are inherently segmentable; they use a signed offset cursor and count each chunk as one section item. The server must emit at least one nonempty Unicode substring to advance an offset. An empty chunk cannot consume source bytes. If a single Unicode scalar plus required metadata/cursor cannot fit, resource_limit terminates that attempt without advancing. Source references and atomic context/header metadata are not silently split across malformed objects; their oversize follows the defined entry-details or resource-limit route.

Examples under one fixed snapshot/scope: `[oversized A, fitting B, fitting C]` can return `[Marker(A), B]` with next_cursor after B, then `[C]`; IDs A/B/C each appear once. `[fitting A, oversized B, fitting C]` can return `[A, Marker(B)]`, then `[C]`. `[fitting A, fitting B which only exceeds remaining page bytes]` returns `[A]` then `[B]`, never Marker(B). `[unrepresentable even as Marker A, fitting B]` yields resource_limit without advancing past A; it cannot claim that B was reachable by a valid continuation. Coverage is incomplete throughout marker pages even if has_more=false because result identity coverage and delivered semantic content are separate.

## Pagination and source-reference identity

Filtering occurs before ranking/page slicing. Let `Q = query_text(request.query)` for nonempty search, preserving case and every interior character; all-whitespace/empty input is explicit browse with `Q = null`. Let `N = normalize(Q)` only when Q is non-null. The exact Q (or its SHA256 of UTF-8), not N alone, defines sequence identity. Use canonical match ordering `(match class, -score, stable ID)` for nonempty search, and require sort `relevance`; nonempty requests with sort `label` are invalid. Browse requires sort `label` and uses stable `(normalized label, stable ID)` order. Direct incident relationship/neighborhood pages sort by relation stable ID. Self-loops occur once. Query/filter/direction/section changes start a new sequence. Do not implement paging by repeatedly requesting the first agent page with a larger limit.

Cursor token is `base64url(canonical compact JSON payload) + "." + base64url(HMAC-SHA256(service_secret, payload_bytes))`; unpadded encoding, one dot, maximum 2,048 bytes. Payload has exact keys `{v:1,service_instance:InstanceId,session_scope:SessionScope,project_id:string,root_scope:Digest,snapshot:Digest,operation:Operation,scope_sha256:Digest,sort:CursorSort,last_key:LastKey,issued:int,expires:int}`. Project ID uses the canonical project-ID grammar. issued/expires are nonnegative safe integers in monotonic milliseconds since this service start; require issued <= now < expires, expires-issued <= 1000*effective cursor_seconds and expiry no later than the session. No browser timestamp sets these values. CursorSort is exactly relevance/label/relation_id/section_order/source_offset, chosen by operation, not a request override.

LastKey has exactly one operation-specific shape:

- Search relevance: `{kind:"rank",class:int,score:int,id:Id}`, class 0..3, score 0..100000. Compare the canonical tuple `(class,-score,id)` and revalidate it against that exact record and Q in the frozen snapshot.
- Browse: `{kind:"label",label_sha256:Digest,id:Id}`. The digest identifies the exact `normalize(record.label)` bytes. Reconstitute the complete `(normalize(label),id)` key from the immutable snapshot after checking the digest; this keeps pathological labels out of the bounded token without changing their sort semantics.
