## Configuration contract

`ontology-explorer.yaml` is optional strict UTF-8 JSON, the repository's supported YAML subset. Reject duplicate keys, NaN, booleans where integers are required, unknown fields, excessive depth/size, and wrong project identity. Missing configuration means valid safe defaults selected from canonical project identity; it is not permission to read another directory. Present-but-invalid configuration blocks new reads. Configuration itself cannot supply file roots, authority, code, markup, arbitrary links, executable hooks, or additional source allowlists.

Exact top-level shape:

```json
{
  "schema_version": 1,
  "project_id": "the-canonical-project-id",
  "presentation_version": 1,
  "starting_ids": [],
  "categories": [],
  "predicate_labels": [],
  "process_views": [],
  "limits": {}
}
```

Only `schema_version` and `project_id` are required; omitted remaining keys take the displayed defaults. The neutral starter uses `project_id: null` with empty mappings and no runtime activation. Null is valid for starter inspection only; active launch requires normal canonical specialization and matching `project_id`. Name/purpose come from canonical configuration, not this file.

Each category is `{id,label,type_ids,entry_ids}`: ASCII CategoryId up to 40 characters, plain label up to 80, unique exact canonical type IDs and entry IDs, at least one selector. Membership is the union of exact declared `@type` matches and exact IDs, intersected with reading visibility. It is a presentation grouping, never an inferred type/hierarchy. Default categories are All plus canonical nonempty type categories, using those canonical type labels. Enumerate eligible concept type records in exact ID order and assign `type-` plus the first 32 lowercase hexadecimal characters of SHA256 of that exact type ID; fail configuration on a digest collision instead of merging identities. Use at most 31 such categories and disclose this presentation cap without implying that undisplayed types are absent; All/search still cover all visible records. The implicit `all` category has empty selector arrays and denotes all otherwise visible reading records; explicit configuration cannot reuse its reserved ID. Do not guess Skills, Roles, or Processes from label substrings. Omit empty configured/default groups from supported context categories; their configuration remains valid and its exact digest stays in the snapshot. A changed snapshot refresh clears an unavailable selected category with a visible explanation. Unsupported auto-derived groups do not appear. At most 32 categories including all, 32 selectors total per category, and 12 starting IDs. Every reference must resolve in the same validated snapshot; type selectors are exact IDs actually appearing in validated @type values, and starting IDs are distinct non-binding/non-relation records. Wrong kinds or unresolved configuration IDs block configuration rather than invent labels. Defaults include only type labels representable within the category Label bound; omitted longer labels remain available through ordinary entry/search. Default-category omissions by count/label limits set context incomplete with field_limit and the fixed results_incomplete diagnostic. This affects category discovery completeness, never canonical data coverage.

`predicate_labels` contains at most 32 unique exact predicate mappings. Its items are `{predicate_id,forward,inverse}` with exact predicate identity and plain reviewed phrases up to 120 characters. `inverse` is string or null. Without a reviewed inverse, incoming reading retains subject-predicate-object sentence order. Friendly labels cannot strengthen `relatedTo` into causality/dependency. This map changes presentation only; predicate definition, ID, qualifiers and direction remain available.

`process_views` has at most 64 unique exact configured process IDs and each item is exactly `{id,field_relations,field_sources,ordered_source}`. Its ID resolves to a non-binding/non-relation record. No process is selected by a prefix/label substring. `field_relations` is an object with optional keys `applicability`, `roles`, `inputs`, `outputs`, `related_skills`, `related_documents`, `prerequisites`; each value is up to eight unique `{predicate_id:Id,direction:"incoming"|"outgoing"}` selectors resolving to canonical predicates. These select only direct incident relations and preserve original direction/qualifiers. `field_sources` is an object with those same optional keys; each value is up to eight unique `{owner_id:Id,reference_id:Digest,extract_locator:Locator|null}` selections. Each reference must resolve to the exact canonical source tuple for the process, one of its explicit bindings, or a record/endpoint actually selected by its configured field relations. The selected locator is the canonical locator when null. A narrower locator is allowed only when exact extraction proves containment within the selected canonical section/range/value; it never expands file access. Reference IDs use the tuple definition below, which excludes snapshot and presentation digest, so no digest cycle exists. Source-mapping review evidence belongs in the exact adoption/change decision.

`ordered_source` is null or exactly `{owner_id:Id,reference_id:Digest,steps:[{number:int,locator:Locator}]}`. It selects one source directly recorded on the process or explicitly bound to it. There are 1..50 unique step locators; number is consecutive 1..N. This is a reviewed designation of the specific process's ordered source and exact step passages, not authored step text. All sublocators must extract exact, contained, nonoverlapping passages in source order and their original text must explicitly support the mapped numeric sequence. Source hash must equal its recorded hash and each mapped number must be present as an explicit numbered step in the extracted text. Ambiguous branching, unsupported containment, stale bytes or partial precedence disable ordered assertions and preserve the missing-order statement. The sources used by mappings are included in selected-input/source bounds and snapshot identity. A new source mapping that is structurally invalid is presentation_invalid; later source change/unavailability is a truthful process evidence state, not config repair. Purpose and scope remain verbatim canonical definition/scope note. Every projected relation/source field carries its exact supporting identities; no field-content string, arbitrary path, runtime NLP or new canonical schema key is added.

`limits` permits only these lowerable keys: `page_items`, `response_bytes`, `request_bytes`, `request_seconds`, `source_excerpt_bytes`, `initial_nodes`, `initial_edges`, `display_nodes`, `display_edges`, `snapshot_bytes`, `selected_input_bytes`, `selected_files`, `source_files`, `records`, `relationships`, `journal_files`, `journal_bytes`, `sessions`, `session_seconds`, `cursor_seconds`. Values must fit the bounds below; an invalid value is rejected, never silently raised. Effective map initial limits also take the minimum of initial/display/API/canonical limits. No browser request changes these server limits.

The configuration file itself is at most 2,000,000 bytes and depth 16, subject to selected-input aggregate limits. presentation_version is exactly 1. Each declared text label is nonempty after trim and contains no C0/DEL control characters; it is always data, never markup. Optional top-level omission uses the displayed defaults; unknown nested keys, duplicate IDs, duplicate keys, invalid types and selectors remain fatal. Neutral null project identity yields configuration_needed only during static starter inspection/launch; wrong non-null identity yields identity_mismatch.

`ONTOLOGY-depo/schema/explorer-v1.json` uses JSON Schema Draft 2020-12 (as in ONTOLOGY-depo/schema/advanced-v1.json) with top-level presentation configuration and named `$defs` for each wire request/response/session/error/cursor/data type. It does not make arbitrary API envelopes valid as configuration. All wire object branches are closed and operation-discriminated; custom semantic validators additionally enforce digest/member/monotonic/canonical-byte rules that JSON Schema cannot express. Python and TypeScript validators follow the same definitions. No new runtime dependency is required merely to parse schema documents. Exact schema bytes and digest are part of package identity; no remote schema resolution occurs at launch or read.

The journal budgets are aggregate across both families; ordinary-only observation is insufficient. This is pure validation, not `_candidate`, `preview`, `publish`, `recover`, advanced validation, or current grant checking. Handle an unreadable/malformed item's unknown targets conservatively as affecting the selected read.
5. A selected-affecting intent without a matching valid complete receipt is unresolved even when canonical bytes are stable, every change currently equals its target, or recovery is absent. A partial recovery without valid matching completion remains unresolved. A valid complete matching receipt supersedes its matching old partial recovery record, which the current writer deliberately retains. Completion requires the exact supported family-specific complete receipt and one matching file record for every proposal change. Ordinary receipt files use `{path,before_sha256,sha256,state:"committed"}`. Integration receipt files use `{path,expected_sha256,sha256}` under `status:"complete",edition:"curator-ontology-1.0.0",operation:"integrate-curator"`; they have no state field. Compare each family's predecessor/target digest fields to the exact accepted proposal without inventing a shared receipt schema. Both families use filenames `ONTOP-[A-Za-z0-9-]{4,100}.json`; the observer retains family plus operation identity to prevent cross-family matching. Verify intent_sha256 over the intent without that field, preview_sha256 over preview without that field, exact proposal payload digest and per-path prior-content SHA. Integration preview additionally embeds the exact proposal. Unknown future family/edition/shape fails closed rather than guessed completion. These pure checks never call writer candidate/grant/recovery code. Never require every historical complete receipt's after bytes to equal today's files; later valid publications legitimately supersede them. Orphan/mismatched receipts or recovery records do not establish completion. An unresolved operation is relevant when it changes the union of old and candidate-selected canonical/module/source/config inputs, or changes configuration capable of selecting those inputs. Uncertain scope fails closed; a proved disjoint historical operation can be excluded with internal evidence.
6. Under that coordination observation, build the canonical view and compare the complete before/after manifests. Include canonical config/context/module manifests/locked module file set/project and binding files/competency inputs, every actual selected source hash or explicit unavailable marker, exact core/helper digests, adapter/schema digests, identity files consulted by the canonical loader, and presentation bytes or absent marker. Also recheck discovered file sets so additions cannot evade digest checks. Do not rely on mtimes. Source-unavailable state must be stable across the observation; transitions retry.
7. Compute the snapshot ID as lowercase SHA256 of canonical serialization of `{schema:1, root_identity_digest, project_id, code_epoch, canonical_context, additional_inputs, adapter_version, presentation_sha256}`. Timestamps are metadata only. root_identity_digest is exactly root_scope_id defined below, and cursor root_scope is that same value; these are field names in distinct internal/wire shapes, not distinct identity algorithms. It is never a browser-supplied identity. The complete manifest stays server-side; responses carry only necessary compact identity/version metadata.
8. Every newly requested current read repeats bounded current-input/coordination validation before using cache. A cached digest match permits index reuse, not skipping byte checks based only on mtime. Changes to selected source observations, canonical data or valid presentation/configuration mappings create a new validated candidate snapshot; they cannot mutate the existing object. Executing helper/adapter/schema/build changes instead trigger the sticky code-epoch drift rule below and never create a new snapshot in the old process. Swap current only after validation succeeds. Existing screens may retain their old snapshot with a visible warning. New data for an old expected snapshot gets `snapshot_changed` rather than mixing records.

Cache keys contain resolved root identity, project ID, snapshot digest, pinned code epoch, helper/adapter version and presentation digest. There is no global cross-project cache. At most two immutable snapshots exist; a third materialization waits within the deadline or returns busy until readers release the retiring view. Every lease releases in `finally`, including cancellation/error. Retired views are released immediately when the last reader finishes; no disk index/cache writes. The session does not pin history indefinitely. Transient source bytes are discarded after hashing or bounded extraction.

Source opening has one deliberate distinction: canonical *source-reference identity* remains bound to the displayed snapshot, but the source body is a fresh observation. If only that authorized source's actual bytes changed, `/source` may return the freshly checked bounded body with `status: source_changed`, the original snapshot/reference/recorded hash, the newly observed hash, and an explicit version-mismatch warning. It must not call those bytes the original cited passage or advance the application's snapshot. Other canonical/config/reference changes still yield `snapshot_changed`. The response includes `data.observation.outside_snapshot: true` when the body's observed digest differs from the snapshot observation. All later ordinary current reads detect that change normally. This preserves AT-20 without making AT-21's source-reference identity ambiguous.

## Startup code epoch and drift

Separate the executing package from reloadable knowledge. At explicit startup, create an execution manifest containing every Python source in the Explorer/core loader import closure, the exact helper file set observed by canonical `Project.context`, Explorer adapter/CLI/schema files, all manifested frontend assets, the runtime asset manifest, package/lock/build identity and schema digest. Include the selected interpreter implementation/version in the epoch. Reject unexpected, symlinked, missing or mismatched members. Compute `code_epoch = SHA256(canonical_bytes(execution_manifest))`; retain the manifest and exact helper digest map in memory. Source/ontology/configuration/presentation inputs are separately classified as reloadable data. A file selected as both source evidence and executable code is executable for drift handling.

The executing closure must identify the actual source bytes loaded, not a rehash of filenames after import. The implementation must start the dedicated service/worker from a clean verified closure, load project-owned Python modules from those exact verified source bytes (compile those bytes through the fixed source loader, with no project `.pyc` reuse or ambient imports), and retain each loaded-byte digest. The supervisor/worker handshake compares the expected manifest/epoch and loaded closure before accepting a session. Already-imported modules of unknown byte provenance are ineligible. Standard-library/interpreter components remain the selected trusted runtime; no canonical document is importable as code. Before and after initial load, recheck the installed package manifest/file set. A browser presenting an old compiled build/schema receives package_changed for that exchange but cannot poison a healthy service; only observed installed/loaded closure drift enters the sticky service state. Drift aborts startup without publishing a usable service session. This is a required implementation invariant, not a claim that the proposed loader exists.

Before every session/read/asset response and before publishing a new snapshot, validate installed executing-code/schema/build bytes and their file sets against the pinned startup manifest. Compare canonical `Project.context().helpers` with the pinned helper map; never substitute changed on-disk hashes into a snapshot executed with old imported modules. A removal, addition within the helper closure, changed code/schema/build byte or loaded-code disagreement enters a sticky `package_changed` state. Revoke sessions/cursors, cancel pending reads, terminate/reap the owned worker and stop serving knowledge/assets. Do not automatically restart into new code, silently hot-reload, reinterpret existing cursors, or issue a new knowledge snapshot. The minimal public health identity may report `package_changed`; its response includes no project data. Host/Origin checks still precede disclosure. A later restoration of old bytes does not clear the sticky state.

The browser retains old readable context and desired route, marks it unavailable for current reads, clears credentials/cursors and asks for explicit fresh local reopening. The launcher must verify a complete new package and start a new service instance and fresh session. No old bootstrap/session/cursor survives. Session exchange requires the browser's compiled `client_build_id` and `schema_sha256` to match the pinned package; old tabs cannot authenticate against a replacement service. Every read request/response carries the pinned `code_epoch`. Its build ID is derived from build inputs before generated assets, with manifest hashes binding the resulting assets, avoiding a circular self-hash. A late response from another epoch is never applied as data.

Only same-epoch ontology, source-observation and valid presentation changes may use Refresh knowledge. These still require the existing transaction/digest/snapshot rules. A worker resource failure may be recovered by at most one later explicit read/reconnect under the same verified epoch, with new worker loaded-byte verification; code drift never uses that recovery. Tests must replace a loaded helper/schema/asset after startup, including an unchanged-mtime replacement, and prove no new response claims the replacement digest while old code runs. Fresh startup and old-client rejection are distinct test cases.

## Closed wire and scalar definitions

The following notation is normative for schema generation. Objects have exactly the listed keys, all required unless a configuration default is explicitly stated. Additional keys are rejected. A union means exactly one listed shape selected by its discriminant; it does not permit mixing branch fields. `T|null` is the only nullable notation. Arrays are JSON arrays, preserve order unless normalization is explicitly required, and satisfy both their stated count and complete-envelope byte budget. Integers are safe JSON integers; booleans and floats are not integers. JSON uses strict UTF-8 with duplicate-key/non-finite-number rejection and depth at most 16. Bounded source/canonical JSON rendered as text is not decoded into an executable object.

## Oversized-item progression

The serializer measures compact UTF-8 bytes of the complete final envelope, including coverage and the actual signed next cursor, before sending. A logical result is either one complete Summary/Edge or one Marker for exactly that identity. page.returned counts both; coverage returned_edges counts only complete Edge values. A marker keeps coverage.complete false, adds item_omitted plus its byte_limit/field_limit/visited_limit reason, displays the exact identity and Open detail action, and is retained visibly when the client appends pages. It does not imply the corresponding statement has been read/rendered completely.

There are three distinct cases:

1. **Deferred only by the remaining page space:** The next complete item fits an otherwise empty legal page under the same scope/limits but not the partially filled current page. Finish the current page. Do not return a marker and do not consume the deferred item's key. next_cursor points after the last actually returned complete item/marker. If bounded lookahead proved the deferred item exists, has_more=true. The next page returns it normally.
2. **Full item cannot fit even an empty legal page:** If a complete item violates a fixed compact-field bound, exceeds a fully empty envelope with the actual needed cursor, or cannot fit its mandatory endpoint-node set in an otherwise empty graph page, construct Marker with field_limit, byte_limit or visited_limit respectively. A relation deferred only because earlier edges consumed the current page node budget instead follows case 1 and is not consumed. If Marker fits, return it as the logical result, consume precisely that item's full stable ranking/relation key, and allow next_cursor to advance past it. Continue to later fitting items within the page count/byte/work bounds. Detail reading uses the named lossless entry section; graph clients never fabricate an edge from a marker. Omission is explicit, not a skipped identity.
3. **Even the marker cannot fit:** If the current page already has logical results, finish that page without consuming this item's key; its next cursor stays after the last returned result and has_more=true when proved. The subsequent empty-page attempt returns resource_limit, returned=0, next_cursor=null and no identity skipped. If no result could be emitted initially, return that bounded error immediately. The request is not retried automatically; the UI offers narrower reading/detail if the selected ID is already known, or the external documented limit-maintenance route. Retrying identical bounds is not described as progress. If a signed cursor alone makes the minimum envelope too large, use the same rule; never omit required scope or weaken its MAC to manufacture a page.

Entry/source text chunks and process text fragments are inherently segmentable; they use a signed offset cursor and count each chunk as one section item. The server must emit at least one nonempty Unicode substring to advance an offset. An empty chunk cannot consume source bytes. If a single Unicode scalar plus required metadata/cursor cannot fit, resource_limit terminates that attempt without advancing. Source references and atomic context/header metadata are not silently split across malformed objects; their oversize follows the defined entry-details or resource-limit route.

Examples under one fixed snapshot/scope: `[oversized A, fitting B, fitting C]` can return `[Marker(A), B]` with next_cursor after B, then `[C]`; IDs A/B/C each appear once. `[fitting A, oversized B, fitting C]` can return `[A, Marker(B)]`, then `[C]`. `[fitting A, fitting B which only exceeds remaining page bytes]` returns `[A]` then `[B]`, never Marker(B). `[unrepresentable even as Marker A, fitting B]` yields resource_limit without advancing past A; it cannot claim that B was reachable by a valid continuation. Coverage is incomplete throughout marker pages even if has_more=false because result identity coverage and delivered semantic content are separate.
