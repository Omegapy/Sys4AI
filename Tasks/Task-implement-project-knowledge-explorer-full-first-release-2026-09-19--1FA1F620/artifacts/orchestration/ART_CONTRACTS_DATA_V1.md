## Configuration contract

`ontology-explorer.yaml` is optional strict UTF-8 JSON, the repository's supported YAML subset. Reject duplicate keys, NaN, booleans where integers are required, unknown fields, excessive depth/size, and wrong project identity. Missing configuration means valid safe defaults selected from canonical project identity; it is not permission to read another directory. Present-but-invalid configuration blocks new reads. Configuration itself cannot supply file roots, authority, code, markup, arbitrary links, executable hooks, or additional source allowlists.

Exact top-level shape:

```json
{
  "schema_version": 1,
  "project_id": "the-canonical-project-id",
  "presentation_version": 1,
  "starting_ids": [],
  "categories": [],
  "predicate_labels": [],
  "process_views": [],
  "limits": {}
}
```

Only `schema_version` and `project_id` are required; omitted remaining keys take the displayed defaults. The neutral starter uses `project_id: null` with empty mappings and no runtime activation. Null is valid for starter inspection only; active launch requires normal canonical specialization and matching `project_id`. Name/purpose come from canonical configuration, not this file.

Each category is `{id,label,type_ids,entry_ids}`: ASCII category key up to 40 characters, plain label up to 80, unique exact canonical type IDs and entry IDs, at least one selector. Membership is the union of exact declared `@type` matches and exact IDs, intersected with reading visibility. It is a presentation grouping, never an inferred type/hierarchy. Default categories are All and supported explicit canonical type categories, named from their canonical labels. Do not guess Skills, Roles, or Processes from label substrings. Empty configured groups may appear with an honest empty explanation; unsupported auto-derived groups do not appear. At most 32 categories, 32 selectors per category, and 12 starting IDs. Every reference must resolve in the same validated snapshot; wrong kinds or unresolved configuration IDs block configuration rather than invent labels.

`predicate_labels` items are `{predicate_id,forward,inverse}` with exact predicate identity and plain reviewed phrases up to 120 characters. `inverse` is string or null. Without a reviewed inverse, incoming reading retains subject-predicate-object sentence order. Friendly labels cannot strengthen `relatedTo` into causality/dependency. This map changes presentation only; predicate definition, ID, qualifiers and direction remain available.

`process_views` items are `{id,field_relations,ordered_source}`. `id` is an exact canonical identity. `field_relations` is an object with optional keys `applicability`, `roles`, `inputs`, `outputs`, `related_skills`, `related_documents`, `prerequisites`; each contains up to eight `{predicate_id,direction}` selectors. There is no arbitrary field-content string. `ordered_source` is null or `{owner_id,reference_id}` selecting an already bound source reference from that process or one of its authorized bindings. At most 64 explicit process entries. Purpose uses the record's definition; scope uses its recorded scope note. Each displayed derived field carries its supporting relation IDs. Mapping provenance belongs in the reviewed adoption/change decision, and the mapping digest belongs in the snapshot.

`limits` permits only these lowerable keys: `page_items`, `response_bytes`, `request_bytes`, `request_seconds`, `source_excerpt_bytes`, `initial_nodes`, `initial_edges`, `display_nodes`, `display_edges`, `snapshot_bytes`, `selected_input_bytes`, `selected_files`, `source_files`, `records`, `relationships`, `journal_files`, `journal_bytes`, `sessions`, `session_seconds`, `cursor_seconds`. Values must fit the bounds below; an invalid value is rejected, never silently raised. Effective map initial limits also take the minimum of initial/display/API/canonical limits. No browser request changes these server limits.

## Transaction coordination and immutable snapshots

An immutable view is a validated `Project` plus compact indexes and the complete selected manifest. It is derived and memory-only, not a new canonical store. Preserve normal `load_project(validate=True)` semantics; never use `validate=False` to make a graph appear usable. Missing-reference validation errors block current reads with precise safe error codes; broken data must not be given invented labels. Current records already validated by the loader can be shown with stale/unavailable source warnings.

1. Resolve the caller-selected root once at startup, reject symlink aliases, and retain its device/inode identity. The browser never selects it. Before materialization or revalidation, open every relevant directory/file through the existing no-follow descriptor pattern. Track absent optional files as explicit absent markers, including `project.json`, the root registry identity observation, and `ontology-explorer.yaml`; appearance is a change.
2. Observe `control_records/ontology/publication.lock` without creating directories or files. If present, open O_RDONLY/O_NOFOLLOW, require regular single-link identity, acquire `LOCK_SH | LOCK_NB` on that existing descriptor, and retain it across journal inspection, materialization, and postcheck. This coordinates with the existing exclusive publisher lock; it introduces no second writer lock path. If busy, retry within the bound or return `knowledge_updating`. Confirm the path still names that inode at the end. Never call `operation_lock` or create a replacement lock.
3. If the lock is absent, capture the nearest existing parent-directory identities and absence explicitly; materialize with before/after journal inventories and selected-byte manifests. Recheck the entire absent-path chain and the lock at the end. If a lock or directory appears, disappears or changes identity, discard and retry using the now-existing lock. A completed supported publication leaves the lock file present, so missing-to-present is observable. If coordination cannot be established because of unreadable/unsafe paths, malformed state, unsupported platform, or journal bounds, fail closed. Do not convert uncertainty to 'no writer'.
4. Read bounded `intents`, `receipts`, and `recovery` inventories using descriptor-relative no-follow reads. Validate operation IDs, supported shapes, intent digest, proposal payload digest, preview digest, prior-content digest bindings, exact target set, and receipt-to-intent/payload/preview identity. This is pure validation, not `_candidate`, `preview`, `publish`, `recover`, advanced validation, or current grant checking. Handle an unreadable/malformed item's unknown targets conservatively as affecting the selected read.
5. A selected-affecting intent without a matching valid complete receipt is unresolved even when canonical bytes are stable, every change currently equals its target, or recovery is absent. A partial recovery without valid matching completion remains unresolved. A valid complete matching receipt supersedes its matching old partial recovery record, which the current writer deliberately retains. Completion requires one committed file record for every proposal change, with matching paths/before/after hashes. Never require every historical complete receipt's after bytes to equal today's files; later valid publications legitimately supersede them. Orphan/mismatched receipts or recovery records do not establish completion. An unresolved operation is relevant when it changes any selected canonical/module/source/config input, or changes configuration capable of selecting those inputs. Uncertain scope fails closed; a proved disjoint historical operation can be excluded with internal evidence.
6. Under that coordination observation, build the canonical view and compare the complete before/after manifests. Include canonical config/context/module manifests/locked module file set/project and binding files/competency inputs, every actual selected source hash or explicit unavailable marker, exact core/helper digests, adapter/schema digests, identity files consulted by the canonical loader, and presentation bytes or absent marker. Also recheck discovered file sets so additions cannot evade digest checks. Do not rely on mtimes. Source-unavailable state must be stable across the observation; transitions retry.
7. Compute the snapshot ID as lowercase SHA256 of canonical serialization of `{schema:1, root_identity_digest, project_id, canonical_context, additional_inputs, adapter_version, presentation_sha256}`. Timestamps are metadata only. The root digest is based on resolved path and device/inode; it is not a browser-supplied identity. The complete manifest stays server-side; responses carry only necessary compact identity/version metadata.
8. Every newly requested current read repeats bounded current-input/coordination validation before using cache. A cached digest match permits index reuse, not skipping byte checks based only on mtime. Changes to sources/config/helpers/mappings or canonical data create a new validated candidate snapshot; they cannot mutate the existing object. Swap current only after validation succeeds. Existing screens may retain their old snapshot with a visible warning. New data for an old expected snapshot gets `snapshot_changed` rather than mixing records.

Cache keys contain resolved root identity, project ID, snapshot digest, helper/adapter version and presentation digest. There is no global cross-project cache. At most two immutable snapshots exist; a third materialization waits within the deadline or returns busy until readers release the retiring view. Every lease releases in `finally`, including cancellation/error. Retired views are released immediately when the last reader finishes; no disk index/cache writes. The session does not pin history indefinitely. Transient source bytes are discarded after hashing or bounded extraction.

Source opening has one deliberate distinction: canonical *source-reference identity* remains bound to the displayed snapshot, but the source body is a fresh observation. If only that authorized source's actual bytes changed, `/source` may return the freshly checked bounded body with `status: source_changed`, the original snapshot/reference/recorded hash, the newly observed hash, and an explicit version-mismatch warning. It must not call those bytes the original cited passage or advance the application's snapshot. Other canonical/config/reference changes still yield `snapshot_changed`. The response includes `observation_outside_snapshot: true` when the body's observed digest differs from the snapshot observation. All later ordinary current reads detect that change normally. This preserves AT-20 without making AT-21's source-reference identity ambiguous.

## Pagination and source-reference identity

Filtering occurs before ranking/page slicing.
