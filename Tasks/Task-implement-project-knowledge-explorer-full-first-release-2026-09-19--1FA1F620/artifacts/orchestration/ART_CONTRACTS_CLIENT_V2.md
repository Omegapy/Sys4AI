## Resource contract

All sizes below are UTF-8 bytes, MiB means 1,048,576 bytes, and elapsed limits use a monotonic clock. Numeric choices are conservative implementation limits to verify, not measured performance results. The canonical settings always win when tighter.

| Resource | Default / hard maximum |
| --- | --- |
| JSON request body | 16,384 / 16,384; decoded depth 12; at most 256 object/list members per container |
| HTTP request target / headers | 2,048 / 16,384 aggregate header bytes, 32 headers; exactly one Host and Content-Length; no Transfer-Encoding or compression |
| API complete serialized response | min(32,000, canonical max_context_bytes); never exceed that after metadata/diagnostics/cursor insertion |
| Page result records | default min(20, canonical default_limit); max min(100, canonical max_limit) |
| Search text | max 4,096 characters and request byte bound; trim with canonical query_text; empty text means explicit alphabetical browse |
| Filter arrays | each max 16 distinct exact IDs/enums; total request bound still applies |
| Neighborhood | depth exactly 1 for first release; initial targets 25 nodes/50 edges, clamped to per-request item/byte/visit limits |
| Visited distinct nodes | min(100, canonical max_limit), counting focus and endpoints; endpoints cannot bypass this cap |
| Cumulative browser graph | max 100 nodes/200 edges, independently constrained by accepted data; no automatic recursive accumulation |
| Per read hard execution deadline | 5 seconds total; at most 3 materialization attempts (initial plus 2 retries), all within that same deadline |
| Header/body read / response write | 2 seconds each, total connection lifetime 10 seconds; disconnect aborts queued work |
| Transport concurrency | 4 admitted connections, bounded backlog 8; no unbounded ThreadingHTTPServer threads |
| Read execution | 1 fixed worker, queue max 4 including active request; bounded busy response at admission |
| Source input / returned excerpt | input max 2,000,000 (existing core ceiling); excerpt at most 12,000 and response budget; longer text is visibly truncated |
| Cursor encoded length / lifetime | 2,048 / min(300 seconds, remaining session lifetime) |
| Sessions / bootstrap tokens | 8 / 8 live maximum; expired entries purged before admission; no eviction of a live user's session |
| Session / bootstrap lifetime | 900 seconds absolute / 60 seconds one-use; no activity-based unbounded extension |
| View cache | max 2 immutable views (current and retiring), logical accounted data max 64 MiB total; no persistent reader cache |
| Worker resource ceiling | RSS limit target 256 MiB, CPU 5 seconds per request, parent-observed deadline; platform enforcement must be verified |
| Selected input admission | max 256 files, each at existing <=2 MB, aggregate <=32 MiB, max 60,000 records; lower existing per-file graph cap 10,000 remains unchanged |
| Coordination scan | each file <=2 MB; aggregate <=16 MiB; max 1,024 operation IDs; overflow fails closed, never skips old unresolved intents |
| Runtime assets | max 64 manifest entries, each <=8 MiB, aggregate <=16 MiB; manifest <=128 KiB |
| Frontend retained data | 8 entry/relationship pages max, 256 KiB each and 2 MiB total; 1 transient source excerpt; 50 safe history states max |

The fixed worker exists because a timed-out synchronous parse cannot safely be canceled by abandoning a Python thread. Launch it explicitly with the service using the selected interpreter and one fixed source module. It receives a server-bound root and fixed operation enum through private bounded IPC, never a browser-selected executable or root. Existing canonical loader semantics remain in that worker. It retains the one immutable view shared by serialized requests, so concurrent callers do not each rebuild the graph. Parent transport queues are bounded, enforce wall deadlines, discard late outputs, and terminate/reap a timed-out worker before any replacement. Replacement follows a later explicit read, at most once per 30 seconds; never create repeated hidden loops. Automatic replacement is part of the already-started service, not permission to restart a stopped service. Failure to establish effective host memory/time controls is a reported unsupported limit, not a claim of enforcement; choose the existing standard-library resource mechanism on the verified target and test actual termination.

Admission enumerates configured and manifested selected files before parsing; source identities discovered from parsed records are added within the same byte/file budgets. A second bounded pass covers those sources and validates the resulting complete view. No source/record scan is unbounded simply because the final response is small. A valid larger ontology can yield `resource_limit` in Explorer without changing canonical loader/agent limits. The approximate 5,000/50,000 stress fixture is a target for honest degradation, not authority to raise canonical per-file capacity.

## Coherent snapshot and transaction observer

Treat the selected root's resolved path, device/inode identity, canonical project/namespace, canonical input hashes, source-reference inventory and current source hashes/status, core/module/context/helper hashes, presentation/config digest (including missing marker), adapter/API version and production build identity as the immutable view key. Snapshot SHA256 is the digest of sorted canonical JSON describing that identity; timestamps alone are never a snapshot. Keep raw root paths server-only. Helpers and installed bundle are pinned at service startup: changes require `service_stale` and fresh launch, not execution of old imported code labeled with a new hash.

Observe the existing publication protocol, not a new writer lock:

1. Resolve/open the selected root and coordination directories using read-only no-follow descriptors. Existing publication.lock may be opened O_RDONLY|O_NOFOLLOW and held with a nonblocking shared flock through the observation/materialization interval. Verify regular single-link identity and compare descriptor and named-path inode. Never call `operation_lock`, O_CREAT, mkdir or recovery as a read.
2. If the lock is absent, record its absence and the nearest existing parent directory identities; recheck these before and after input reads. A missing-to-present lock or directory/lock inode change causes retry. Existing publishers retain their lock file; absence across the interval plus stable selected bytes/journal inventory covers a pristine installation. If that protocol cannot be established, fail `knowledge_updating` rather than inventing coherence.
3. Inspect both `control_records/ontology/{intents,receipts,recovery}` and `control_records/ontology/integrations/{intents,receipts,recovery}`. Strictly validate bounded filenames/schema, operation identity, intent digest, proposal/preview hashes and the complete-receipt correspondence. Compare targeted paths against the union of old/new selected paths, config and modules; a config transaction is relevant even when it introduces a not-yet-selected file. Unknown/malformed scope fails closed.
4. A relevant accepted intent without its matching complete receipt is unresolved even when there is no live writer, all currently readable hashes are stable, or all replacements apparently succeeded. A partial recovery record does not become complete because processes are absent. A corresponding valid complete receipt resolves a retained older recovery marker; do not require deletion of historical recovery. Historical completed receipts are validated as evidence of their own operations, not compared as if their targets must still equal every old version after later legitimate publications. Unknown supersession does not resolve an incomplete operation.
5. Under that observation, materialize with the existing validated core loader and construct incoming/outgoing indexes, compact summaries and source registry from its immutable records. Re-read all selected bytes, current source status and hashes, helper/config identities and coordination directory membership/content fingerprints before accepting. Configuration change requires rediscovering its selection on a bounded retry. Hold the shared lock where present through both passes.
6. Accept only if the full identity and relevant completed/unresolved classification are stable. Otherwise retry at most twice under the single 5-second deadline, then `knowledge_updating`. No partially assembled view is published.

A fresh current read revalidates selected inputs by bytes; mtimes can be hints but not proof. Expensive hashing can share one in-progress validation among bounded concurrent callers, never omit it. Old coherent content may remain in the browser with its original snapshot and visible update warning. The server does not satisfy a new requested snapshot with data from another view. New data only enters via explicit Refresh knowledge, which atomically replaces entry, relationship and map data and clears incompatible expansions/cursors/source body. Invalid canonical config blocks new reads rather than silently falling back.

Each immutable view has a reference count. Retiring views are released when active serialization finishes, and at most one old view may coexist with current materialization. If the limit is reached, return busy rather than create a third. IPC/results contain detached JSON, not references that permit mutating the cached core Project. Source excerpts are not cached between operations. Shutdown clears all caches/session/cursor material.
