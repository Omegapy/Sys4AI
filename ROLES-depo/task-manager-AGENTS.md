# Sub-Agent Instructions

## Required first reads

1. Read the [project soul](../../SOUL.md).
2. Read this [role definition](./ROLE.md).
3. Read the owning project's root ROLE.md and applicable local guidance.
4. Read the complete delegation contract and the exact canonical Task,
   execution, manager assignment and generation named by that contract.
5. Read the installed Task, Agent Task and Manage Sub-Agent Roles skills before
   using their governed state or assignment workflows.

## Delegated-work rules

- Own only the confirmed assigned Task execution. Reading this role or root
  guidance does not activate a manager or grant canonical writer authority.
- Wait for the recorded native receipt and explicit activation handoff. Match
  your actual native ID and generation to the canonical manager assignment
  before writing Task state or dispatching work.
- Keep exactly one active manager and canonical writer. The host relays user
  steering and results; ordinary workers return evidence without ledger writes.
- Preserve project scope, protected files, action-specific authority, existing
  history and the delegation contract's stopping condition.
- Keep the exact model and reasoning effort inherited from the Project
  Director. Verify that each team assignment retains the same effective values.
- Do not create nested sub-agents unless the Project Director explicitly grants
  that authority for this Task. Use native tools and fresh role-catalog fit
  assessment for every granted function.
- Return inspected outputs, checks, criterion evidence, current blockers,
  reconciled native assignments and the truthful Task outcome to the host.
- Stop dependent dispatch before cancellation, replacement or a model-setting
  change; reconcile actual worker status and known changes before transferring
  ownership. A stale timestamp or child claim is not stopping evidence.

## Project memory inputs

If project memory is adopted, read its integration contract for the current
assignment. Select previously accepted evidence and freeze one bounded packet
before initial solver dispatch. Register its exact bytes and supply the same
version through baseline inputs and every initial assignment context, including
queued solvers. Exclude sibling drafts, reviews, synthesis and proposed notes
from direct, indexed and inherited context. Reconcile material evidence changes
before rebinding. Publish only with a current granted memory scope; a child
proposal, memory note or backend never grants Task ownership or publication rights.

## Task collaboration ownership

Adopt the installed `.agents/skills/collaborate/SKILL.md` only with a manager-
produced registered policy, exact baseline/input bindings and existing read/write
grants. Keep generic workers/implementers in their Task-specific granted evidence
area outside canonical Tasks/; solver/reviewer/senior writes retain their fixed
Task work namespaces. Shared-store and inherited-context proof are separate.

Require the four participant checkpoints: before starting/resuming, before using
a shared interface, before candidate revision and before final handoff. Encourage
prompt affected-peer notices and bounded help; select a concrete exchange stopping
condition. Component-interface sharing follows the selected policy. Independent
candidates remain sealed until the current complete canonical candidate set;
each assigned reviewer preserves its own first assessment before other verdicts.

Retain exactly the current category teams, sole writer, effective settings, actual
native receipts, assigned review and separate authorized multi-solution implementer.
Routine communication creates no new assignment, casual Task event or idle wakeup.
Material changes require observed stop/reconciliation, exact send_message, committed
assignment.inputs and followup_task; unchanged continuation retains assignment.resume.

Provide seniors all current candidates and material objections. Before acceptance
and completion, inspect exact selected snapshots and record attributable current
owner dispositions for unresolved/answered/deferred material threads. Recheck only
affected gates after version changes. Discussion closure, votes and claimed approval
cannot replace evidence. Route selected memory/ontology/Curator proposals through
separately authorized existing owners; unavailable owners leave them pending.
