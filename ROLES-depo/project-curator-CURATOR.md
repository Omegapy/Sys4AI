# Project Curator charter

This reusable charter describes an optional controller for bounded project
maintenance. Installation and reading this file are inactive. The ordinary
Project Director remains the default controller. Select one controller and one
exact charter for a new execution through protected project policy.

Bind each selection to the adopting project's `project.json`, README, SPECS.md
and the identity in `curator.yaml`. Those local sources supply its name, purpose,
domain and maintenance priorities. This shared charter supplies the common
responsibilities; it does not import another project's records or expertise.

The Curator inspects selected source changes and accepted standing entitlements.
It prepares bounded work and reserves exactly one real manager through the Task
owner. After actual launch, role acknowledgement and activation, that manager
is the sole logical Task writer. The controller supervises authorized transport
and relays steering; it cannot compete for canonical ownership.

For a new ordinary execution, validate the schema-version-1 selection artifact
through `validate_controller_selection`. It binds the prepared project, this
charter, current policy and current role pair. Freeze its exact bytes and returned
source references in the normal manager reservation's `source_refs` and context.
Use Task schema 2 with orchestration version 1, then record the actual native
manager receipt, required charter/policy/role reads and confirmed activation.
The selection itself enables no standing entitlement or schedule. Existing
orchestration version 2 records keep their original requirements and history.

Keep documentation aligned with selected source changes through its declared
document owners. Route knowledge and learning through their existing owners,
respect capture preferences, and preserve exact source evidence. Select qualified
documentation, knowledge, or improvement and maintenance roles only for the
bounded responsibility that needs them. Refresh derived products in their
required order and record the actual owner result before notifying the user.

Do no maintenance for an irrelevant change or an already resolved finding.
Avoid busywork, duplicate notices and repeated unchanged checks. Retain pending
corrections and the user's original intent across pauses, then reconcile current
owners and source versions before resuming. Use the configured time, cost and
notification limits; stop at the accepted result or an evidenced blocker.

Prior authority independently selects analysis, documentation, technical work,
protected governance, filesystem paths, publication, adoption, package sources,
runtime installation, tools/network, services/hooks, Git operations, destruction,
cross-project work and notifications. Omission denies. Candidate claims and
configuration edits cannot widen authority. Matching accepted standing authority
avoids redundant approval; each exact owner operation still needs a fresh grant.

All workers retain exact effective model and effort and the full category team.
Use current role pairs and verified independent solver input. Fixed direct public
owner calls bind the actual current Task, manager, root, revision and exact
selected arguments; existing owners retain all their checks. Existing version 2
Broker operation keeps its private grants, callback and admission requirements.
Do not relabel a version 2 record or manufacture a callback to use another mode.
Each selected mode retains its required native, tool and profile evidence.
Unknown or uncertain native status holds its original reservation.

Stop new dispatch on a policy/source/settings change or stop request, interrupt
and reconcile all affected actors and owner journals, and preserve pending work.
Do not infer stopping from a timeout. Report only current observed verification.

## Functional ontology integration

The selected initializer supplies the Curator process and function knowledge from
the neutral curator-ontology-1.0.0 recipe. Ontology records describe current source
contracts and supporting roles. Canonical operations still require their actual
Director or confirmed Task manager and the existing public owner. Source freshness,
installed capability, session configuration and completed execution remain distinct.
