# Task Requirement Document: Document-centric To-TRD lifecycle

## Destination

Redesign To-TRD as a document-lifecycle tracker. It must report whether a Task Requirement Document is still being drafted, is complete as an approved requirements artifact, or is retired; it must not track whether the requirements have been implemented.

## Captured user intent

U01 — The user rejects the current `not_done` state because it represents implementation work remaining after the requirements document has already been completed.
U02 — The user requires the completed-document state to be called `trd_done` rather than `not_done`.
U03 — The governed artifact remains a Task Requirement Document, or TRD; the user's temporary reference to PRD was corrected explicitly.
U04 — The user normally sends a completed TRD to To-Implementation-Plan, so implementation planning and implementation progress must remain outside To-TRD.
U05 — The user explicitly opened a new tracked Task for this lifecycle redesign rather than reopening or extending the completed Memory System requirements Task.
U06 — The user's direction that `not_done` must become `trd_done` and that To-TRD tracks the TRD itself requires a clean document-state cutover rather than a compatibility alias that preserves implementation-state behavior.

## Context and sources

S01 — `SKILLS-depo/to-trd/SKILL.md`, `ACTIONS.md`, and `references/trd-contract.md` currently define `draft`, `not_done`, `done`, and `retired`, where `not_done` means the baseline is settled but work is unfinished and `done` requires implementation-completion evidence.
S02 — `SKILLS-depo/to-trd/scripts/trd.py` embeds those states in its status enum, transition graph, readiness and completion gates, update behavior, CLI choices, catalog counts, sorting, action mapping, and index explanation.
S03 — `SKILLS-depo/to-trd/assets/trd-body-template.md` and the helper parser require a completion checkbox and Evidence field for every requirement plus a document-level Completion evidence section.
S04 — `SKILLS-depo/to-trd/tests/test_trd.py` directly exercises all legacy lifecycle pairs, implementation-evidence completion gates, automatic return from `not_done` to `draft`, CLI status values, action IDs, and index behavior.
S05 — Live inspection on 2026-09-04 found content-equivalent To-TRD packages at `SKILLS-depo/to-trd/`, `.agents/skills/to-trd/`, `Projects/Sys4AI-Template-Project/.agents/skills/to-trd/`, `Projects/Sys4AI-Memory-Service/.agents/skills/to-trd/`, and `Projects/Sys4AI-Electronics-Projects/.agents/skills/to-trd/`, excluding `.DS_Store` and generated bytecode caches. Project-local copies remain separately owned and are not automatically synchronized.
S06 — The root catalog contained three managed TRDs before this redesign draft was created and now contains four: three `draft`, one `not_done`, zero `done`, and zero `retired`; `TRD-20260904-2D10A556` is the current `not_done` record.
S07 — `.agents/skills/to-implementation-plan/` accepts a TRD as an immutable source observation and owns a separate plan lifecycle, requirement status, task status, and implementation-evidence model.
S08 — `TASK-20260904-9702FDD5` governs this requirements-definition work and prohibits implementation, existing-record migration, dependency installation, destructive operations, Git actions, publication, and deployment.
S09 — Root `AGENTS.md` and `README.md` require exact source and destination adoption boundaries and prohibit inferred propagation from reusable collections into project-local copies.
S10 — Live migration inventory on 2026-09-04 found six managed TRDs across the root and Electronics catalogs, five `draft` and one `not_done`; none has a checked requirement, meaningful per-requirement Evidence, or non-placeholder Completion evidence.
S11 — `TASK-20260902-1720B124` records the prior explicit adoption of To-TRD from `SKILLS-depo/to-trd/` into the active root and registered template while deliberately leaving the Electronics copy outside that adoption scope.
S12 — The bounded initial delivery chain for this root-requested redesign is therefore the reusable source, active root installation, and registered template installation; the Memory Service and Electronics installations retain independent project ownership and require later explicit adoption.

## In scope

- Define document-centric To-TRD lifecycle states, transitions, readiness gates, revision behavior, and user-facing language.
- Remove implementation-progress and implementation-evidence ownership from To-TRD requirements, document status, actions, CLI, and projections.
- Define a safe versioned compatibility and migration contract for existing managed TRDs.
- Preserve To-Implementation-Plan as the downstream consumer of a completed TRD and preserve Task as the orchestration and performed-work tracker.
- Define the reusable source, active root, and registered template as the bounded initial delivery chain while preserving every other project-local copy.
- Define source, helper, documentation, metadata, tests, catalog, and validation outcomes needed for a future implementation plan.

## Out of scope

- Implementing the To-TRD redesign or modifying any To-TRD package during this requirements Task.
- Migrating an existing TRD or changing `TRD-20260904-2D10A556` during this requirements Task.
- Changing To-Implementation-Plan or Task lifecycle semantics beyond the minimum future compatibility contract needed for TRD handoff.
- Automatically propagating a reusable To-TRD revision into any project-local installation.
- Adopting the revised package into the Memory Service, Electronics, or another independently owned project during the initial delivery.
- Treating `trd_done` as implementation authorization, implementation progress, implementation completion, deployment completion, or release completion.
- Dependency installation, destructive action, Git operation, publication, or deployment.

## Task requirements

### REQ-001 — Track the TRD document lifecycle
- Requirement: Make To-TRD authoritative only for the lifecycle of the TRD document and its approved requirements baseline, not for implementation of those requirements.
- Source: U01 through U04 — the user explicitly separated TRD completion from downstream planning and implementation.
- Acceptance: Every lifecycle definition, command description, generated projection, and agent instruction describes document drafting, document completion, or retirement and contains no claim that To-TRD owns implementation progress or completion.
- Depends on: None.

### REQ-002 — Use the three document states
- Requirement: Use only `draft`, `trd_done`, and `retired` as canonical lifecycle states for newly created or fully migrated TRDs.
- Source: U01 through U03 and the document-centric design consequence of removing implementation state.
- Acceptance: The canonical schema, helper status enum, CLI choices, list filter, receipts, index counts, sorting, documentation, and tests emit exactly the three states and identify `trd_done` as the completed-document state.
- Depends on: REQ-001

### REQ-003 — Define draft as unresolved document content
- Requirement: Define `draft` to mean that the TRD's intent, scope, requirements, acceptance criteria, decisions, assumptions, or other readiness content still requires review or clarification.
- Source: U01 and current draft behavior retained as a document concern.
- Acceptance: A new TRD starts in `draft`; unresolved declarative content or unconfirmed assumptions prevent transition to `trd_done`; no implementation state is considered when determining draft status.
- Depends on: REQ-001

### REQ-004 — Define trd_done as document completion
- Requirement: Define `trd_done` to mean that the exact TRD revision is complete as a requirements document and has received current explicit user approval.
- Source: U01 and U02 — the user selected TRD completion rather than work-remaining semantics.
- Acceptance: A transition to `trd_done` requires at least one valid requirement, `Open questions` and `Not yet specified` set to `None.`, no unconfirmed assumptions, an exact current content digest, a nonblank reason, and explicit user confirmation; it does not require implementation evidence or completed product behavior.
- Depends on: REQ-002, REQ-003

### REQ-005 — Preserve retirement as a document state
- Requirement: Retain `retired` to mean that the TRD is no longer active but remains preserved and discoverable without implying implementation success or failure.
- Source: S01 and U01 — retirement remains a valid document concern.
- Acceptance: Retired TRDs remain in the catalog, retain identity and content, cannot be updated directly, and can return only to `draft` through an explicitly confirmed restoration.
- Depends on: REQ-002

### REQ-006 — Use document-only transitions
- Requirement: Permit `draft` to transition to `trd_done` or `retired`, permit `trd_done` to transition to `draft` or `retired`, permit `retired` to transition to `draft`, and preserve same-state requests as validated no-ops.
- Source: U01 through U04 and the proposed three-state document model.
- Acceptance: Every allowed transition succeeds only with current identity, digest, reason, and confirmation preconditions; every prohibited transition fails without mutation; the transition graph contains no implementation-progress state.
- Depends on: REQ-002, REQ-004, REQ-005

### REQ-007 — Remove legacy implementation states and gates
- Requirement: Remove canonical `not_done` and `done` lifecycle semantics and remove the gate that requires checked requirements and implementation evidence before a TRD can reach its completed-document state.
- Source: U01 and U02 — the user rejects implementation tracking in To-TRD.
- Acceptance: New and migrated schema-version records never emit `not_done` or `done`; no To-TRD transition checks whether product requirements were implemented, tested, deployed, or otherwise satisfied.
- Depends on: REQ-001, REQ-002

### REQ-008 — Keep requirements declarative
- Requirement: Store each TRD requirement as a sourced, bounded, acceptance-testable statement with dependencies, but do not store an implementation-completion checkbox or implementation Evidence field as part of the active requirement schema.
- Source: U01 and S03 — the current per-requirement completion fields belong to the rejected implementation-tracking model.
- Acceptance: Newly rendered requirement blocks retain stable ID, readable title, Requirement, Source, Acceptance, and Depends on fields and omit the completion checkbox and Evidence field; validation no longer counts or gates on completed requirements.
- Depends on: REQ-001, REQ-007

### REQ-009 — Remove document-level implementation evidence
- Requirement: Remove the active `Completion evidence` section and any helper rule that interprets it as proof that the requirements were implemented.
- Source: U01 and S03 — document lifecycle must not double as implementation verification.
- Acceptance: New-schema TRDs neither require nor render `Completion evidence`; document approval is represented through lifecycle metadata and explicit confirmation, while implementation evidence remains in its owning plan and Task systems.
- Depends on: REQ-001, REQ-007

### REQ-010 — Return materially revised TRDs to draft
- Requirement: Return a `trd_done` document to `draft` when its title, intended outcome, scope, exclusions, requirements, acceptance criteria, dependencies, decisions, or other approval-bearing meaning changes.
- Source: U01 and the current conservative scope-change rule retained as document review behavior.
- Acceptance: A material managed update atomically records the changed document and `draft` state with a clear reason; a proven non-material representation-only no-op does not change status, revision, or timestamps.
- Depends on: REQ-003, REQ-004

### REQ-011 — Introduce an explicit schema-version migration
- Requirement: Version the document-centric contract separately from legacy schema version 1 and provide an explicit, validated migration path rather than silently rewriting TRDs during read-only commands.
- Source: S01 through S06 and root data-integrity requirements.
- Acceptance: Read-only show, list, and validate never mutate a legacy record; each legacy record is either read with an explicit compatibility classification or reported with a precise migration requirement; a migration requires exact target selection and stale-write protection and produces a reviewable receipt.
- Depends on: REQ-002, REQ-007, REQ-008, REQ-009

### REQ-012 — Define deterministic legacy state mapping
- Requirement: Define a deterministic migration in which legacy `draft` remains `draft`, legacy `not_done` becomes `trd_done`, legacy `done` becomes `trd_done`, and legacy `retired` remains `retired`.
- Source: U01, U02, U04, and U06 — both legacy settled states identify an already approved TRD baseline, and neither implementation-oriented label remains part of the new document lifecycle.
- Acceptance: Migration tests cover every legacy state and prove the mapped document state, preserved identity, monotonic revision and timestamps, recorded migration reason, regenerated index, and absence of an implementation-completion claim.
- Depends on: REQ-011

### REQ-013 — Fail closed on meaningful legacy implementation records
- Requirement: Remove legacy placeholder completion checkboxes and evidence fields during migration, but stop without mutation if a selected TRD contains a checked requirement or meaningful implementation evidence rather than guessing how to transform that historical record.
- Source: U01, S03, S06, and S10 — the inspected catalogs contain only placeholders, while project data-integrity rules prohibit silent loss for any future evidence-bearing record.
- Acceptance: All six observed TRDs qualify for deterministic placeholder removal; a fixture containing a checked requirement, meaningful Evidence line, or meaningful Completion evidence is rejected before canonical or index mutation and reports the exact blocking record and field.
- Depends on: REQ-008, REQ-009, REQ-011

### REQ-014 — Update commands, actions, and projections coherently
- Requirement: Update To-TRD CLI choices, action descriptions and IDs, receipts, counts, ordering, index explanations, help text, README, skill instructions, wayfinding guidance, and agent metadata to the document-centric lifecycle.
- Source: S01, S02, and S04 — the legacy semantics are repeated across the complete package surface.
- Acceptance: A whole-package search finds no active instruction or emitted behavior that presents `not_done` or implementation-completion `done` as current states; `set-status` and `list --status` reject both legacy tokens; and retained legacy terms occur only in explicitly labeled migration readers, documentation, fixtures, and tests.
- Depends on: REQ-002, REQ-007

### REQ-015 — Preserve the implementation-plan handoff
- Requirement: Treat a `trd_done` TRD as a settled source suitable for creating an implementation plan while leaving plan readiness, plan execution, requirement satisfaction, and implementation evidence entirely within To-Implementation-Plan and Task.
- Source: U04 and S07 — the user uses the completed TRD as the source for the next governed workflow.
- Acceptance: Integration checks show that a `trd_done` source can be inspected with its ID, revision, digest, and document state; a draft TRD remains visibly unsettled; neither source observation changes the TRD or grants implementation authority.
- Depends on: REQ-004, REQ-011

### REQ-016 — Use the bounded initial delivery chain
- Requirement: Implement the redesign first in `SKILLS-depo/to-trd/`, then adopt that exact reviewed package into `.agents/skills/to-trd/` and `Projects/Sys4AI-Template-Project/.agents/skills/to-trd/`, while leaving every other project-local installation unchanged.
- Source: S05, S09, S11, and S12 — reusable source and the previously established root-and-template adoption path are distinct from independently owned project copies.
- Acceptance: The future implementation plan names the exact reusable source and both authorized destinations, records before-and-after digests, verifies all three package trees independently, proves the Memory Service and Electronics copies retain their pre-work digests, and creates no automatic synchronization relationship.
- Depends on: REQ-014

### REQ-017 — Replace lifecycle tests rather than weaken them
- Requirement: Replace legacy implementation-tracking tests with complete document-lifecycle, migration, stale-write, path-safety, projection, compatibility, and handoff coverage while preserving unrelated valid To-TRD behavior.
- Source: S04 and project testing discipline.
- Acceptance: Tests cover all allowed and prohibited state pairs, readiness failures, explicit confirmation, same-state no-ops, material revision fallback, all legacy state mappings, fail-closed handling of an evidence-bearing legacy record, CLI filtering, index counts and order, partial index recovery, and To-Implementation-Plan source handoff; the full package suite passes.
- Depends on: REQ-006, REQ-011, REQ-012, REQ-013, REQ-014, REQ-015

### REQ-018 — Migrate the root catalog under explicit authority
- Requirement: Define an explicit root-catalog migration that validates all current TRDs before and after migration and specifically changes `TRD-20260904-2D10A556` from legacy `not_done` to `trd_done` without changing its approved requirements meaning.
- Source: U02, S06, and the data-integrity migration requirement.
- Acceptance: A future authorized migration produces before-and-after identities, revisions, digests, states, and index status for all four current root TRDs; the three draft records remain draft during mechanical migration, the current not_done record becomes trd_done, no record is omitted, and the catalog validates with a current index; after migration, this redesign TRD can enter trd_done only through its own exact-revision approval transition.
- Depends on: REQ-011, REQ-012, REQ-013, REQ-017

### REQ-019 — Keep document completion separate from execution authority
- Requirement: State throughout the workflow that `trd_done` proves only that the TRD document is complete and approved and does not authorize planning, implementation, installation, migration, Git activity, publication, deployment, or external action.
- Source: U04, S07, and the governing separation among TRD, plan, Task, Git, and deployment state.
- Acceptance: Skill instructions, lifecycle contract, help and result wording, and integration tests preserve the separate explicit activation and authorization gates for To-Implementation-Plan, Task execution, and every external or destructive operation.
- Depends on: REQ-001, REQ-004, REQ-015

## Decisions

- D-001 — Keep the artifact name Task Requirement Document and the acronym TRD; do not rename it PRD. Basis: U03.
- D-002 — Make To-TRD track document lifecycle rather than implementation lifecycle. Basis: U01 and U04.
- D-003 — Use `trd_done` as the canonical machine-state spelling of the user's requested “TRD done” state. Basis: U02 and the existing snake-case metadata convention.
- D-004 — Remove implementation-progress ownership from To-TRD and leave it with To-Implementation-Plan and Task. Basis: U01 and U04.
- D-005 — Keep reusable source and project-local adoption as separate authority boundaries. Basis: S05 and S09.
- D-006 — Perform no package implementation or record migration under the current requirements-definition Task. Basis: S08.
- D-007 — Use a clean cutover: ordinary new CLI operations accept only `draft`, `trd_done`, and `retired`; legacy `not_done` and `done` are recognized only by explicit migration logic and both map to `trd_done`. Basis: U01, U02, U04, and U06.
- D-008 — Remove legacy placeholder progress fields during migration and fail closed on any meaningful implementation record instead of creating a new To-TRD evidence archive. Basis: S10 and project data-integrity rules.
- D-009 — Limit initial implementation and adoption to `SKILLS-depo/to-trd/`, the active root installation, and the registered template installation; preserve the Memory Service, Electronics, and every other project-local copy for separately authorized adoption. Basis: S09 through S12.
