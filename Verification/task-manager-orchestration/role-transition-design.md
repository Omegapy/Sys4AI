# Role storage and adoption design

`roles/<name>/AGENTS.md` and `ROLE.md` become the active authoritative pairs.
`roles/INDEX.md` is a deterministic view of a fresh validated catalog. It lists
each valid name, description, pair links and both content digests, plus invalid
bundle diagnostics. Links are relative to the index's owning project; the
index does not authorize an invalid, missing or changed pair.

The existing role helper gains these bounded routes:

- `reindex --format json`: validate live pairs, render stable UTF-8/LF bytes and
  atomically publish the index under a mutation lock. An unchanged second run
  is a no-op. Invalid entries remain diagnostics and never become eligible.
- `transition-preview --format json`: inspect only the legacy immediate role
  pairs and corresponding `roles/` targets. Return exact source/destination
  hashes, collision diagnostics and a digest-bound proposed transition.
- `transition-apply --preview-file FILE --confirmed --format json`: reread the
  preview under the mutation lock, reject changed sources/destinations, and
  copy only the approved pairs. Keep legacy bytes. Publish provenance at
  `roles/.transition.json`, validate the result and regenerate the index.

The implemented help defines final payload fields. Unsupported versions,
unknown fields, unsafe paths, symlinked roots/pairs/index/receipt/locks, duplicate
names and conflicting targets fail without overwrite. An identical target is
attributable existing content; a differing target blocks the transition. Missing
new `roles/` is eligible only for an explicitly confirmed transition, not a
read-only implicit migration.

Creation still uses the existing role templates and validated pair format. A
valid committed bundle survives an index publication failure. Its result
reports bundle commit separately from the pending index and names `reindex`
as recovery; it never asks the caller to create the same role again. A partial
transition retains its reviewed source/target mapping and completed stages;
recovery rechecks those bytes and completes only the remaining publication.
No recovery steals an active lock, overwrites customization or deletes a valid
role. Read-only list/show/validate compare index bytes and report drift without
writing a file or running migration.

## Source and destination ownership

Root's fresh catalog contains only `project-sub-agent`. Its role excludes
Director decisions and Task ownership, so a dedicated reusable `task-manager`
pair is justified. The new role owns only its confirmed Task execution and
granted nested delegation. General workers keep bounded authority and never
become manager by reading root guidance. No example solver/reviewer/senior
roster is installed without a demonstrated reusable gap.

The source pairs live in `ROLES-depo/`. The new helper renders and validates
them in a disposable role tree before source publication. The Template mapping
changes the generic pair destinations to `roles/project-sub-agent/` and adds
the manager pair in `roles/task-manager/`. The updater computes the Template's
index from its destination pairs and records the generated bytes in its normal
hash-managed state. It does not mirror a static index from another context.
Required-file validation changes with the mappings. Legacy mapped retirements
are reviewed with their exact old hashes and retain recovery provenance.

The initializer updates its source scanner, role package boundaries, skipped
customized-package handling, starter policy and receipt compatibility together.
It copies paired roles and generates an index for the destination. It excludes
role-transition runtime metadata, native IDs, active assignments and live Task
history from starters. Prior setup receipts with `sub-agent-roles` retain their
meaning; customized or legacy existing projects require a reviewed transition
before adopting the new active layout. `prepare-existing` never overwrites or
migrates such packages silently.

The active root receives a staged exact patch after Template verification.
That patch preserves its depot ownership and existing ROLE edits, automatic
Task matching/creation and the 30-day `close-old-task` policy. Common orchestration
changes are applied without replacing the root helper with the generic source
helper. Root historical Task records are not selected for schema upgrade.

## Verification cases

Check absent, valid, invalid, duplicate and symlinked role pairs; stale/forged
indexes; deterministic reindex and read-only tree hashes; existing and concurrent
creation; failure between bundle and index publication; and stale/conflicting/
interrupted role transition. Reopen each retained legacy pair and historical
reference after recovery. Check actual root/Template manifests, initializer
receipt compatibility and a clean disposable project before adoption claims.
