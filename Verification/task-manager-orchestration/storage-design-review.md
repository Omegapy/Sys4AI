# Orchestration storage design review

Reviewed the storage contract against all 37 approved TRD requirements and DEC-002 through DEC-005. The contract covers the intended workflow, but the following details must be fixed before it is an executable storage contract. These are design findings, not claims that the unimplemented helper already supports the proposed API.

## Material omissions

1. **Writer checks need one common boundary for every mutation.** The contract names ordinary responses and lifecycle commands, but omits projection rebuild, transaction recovery, response redaction, selected-record upgrade, and root intake. `record-response` and `update` can also set `status_after`; checking only the named `complete`, `pause`, or `cancel` command is insufficient. Root age closure calls the response transaction internally. Enforce actor/generation and resulting-state gates under the locks, with narrowly distinguished recovery operations. Sources: contract lines 41-59; source helper `validate_response_payload` at 1706, `response_transaction` at 1872, `command_rebuild` at 2056, `reconcile_transaction` at 2332, `reconcile_response_redaction` at 2510; installed `command_intake` at 2172. REQ-023, 027, 030, 035-036.

2. **Writer transfer and failed-manager recovery need an exact transition.** Bootstrap loses ordinary write authority at activation, yet the contract does not identify who can recover a stopped or unavailable manager. Keep native user-input relay and interruption outside storage. A recovery transaction may atomically revoke the old writer and transfer to bootstrap only after the old manager and all required owners have current stopping/change evidence. An unavailable or uncertain owner blocks transfer. Never let a generic `actor` flag bypass this rule. REQ-002, 023, 035; DEC-005.

3. **Freeze the required logical team and separate writer from producer.** Without a stored planned solver set, “every candidate” can accidentally mean only candidates returned so far. Preserve a logical solver slot across an authorized native replacement and map each extra-complex solver slot to one distinct reviewer slot. All canonical events are written by the manager; a review's producer is its reviewer assignment, not the event actor. Record delivery evidence for the identical conflict version to every solver. REQ-007, 010, 012-017, 019, 024, 032.

4. **Invalidation must include the Task baseline and review context.** Ordinary edits to Task description/criteria, changed required inputs, a new upstream deliverable, and a conflict requiring renewed attestation must invalidate affected current eligibility. Candidate digest alone is insufficient when the conflict context changes but an unaffected candidate's bytes do not. Use baseline and round identities; recompute eligibility from exact references rather than accepting writable `eligible` or `passed` shortcuts. REQ-004-005, 011, 015, 025, 027.

5. **Recovery must compare exact states and must finish publication without replay.** Current transaction recovery branches principally on revision and can canonicalize `planned_state` before rejecting unknown keys; `canonical_state` selects known fields. Schema-2 intents must validate the complete planned shape first and bind pre-state, post-state, event and artifact digests. Contract line 149 should permit repair of the exact missing recorded publications, including a response or staged artifact, while forbidding reapplication of the event or native launch. Checking the original bootstrap against the post-activation writer would otherwise strand a successfully committed handoff. REQ-030, 033; DEC-002-005.

6. **The age-policy guard must precede matching as well as closure.** Installed `select_intake_match` at 2107 excludes age-eligible records from its active match set before `command_intake` closes them. Merely blocking closure later can still select a successor for an execution with an unresolved owner. Preflight owner reconciliation before excluding an old matching record or committing any generated closure. Preserve installed-only age status, conclusion, matching, partial receipts, and the 30-day threshold; do not add this policy to source/Template. REQ-028, 033, 036.

## Recommended exact first schema

Keep the existing schema-1 field tuple, ordering, response parser, lifecycle semantics, and read-only routes. Schema 2 adds exactly `orchestration`. Validate version-specific exact keys before ordering; reject booleans as integer versions, unknown versions, unknown fields, duplicate JSON keys, and unsafe paths. Do not require actor fields or current role files to make historical schema-1 records readable.

Use `orchestration = {version: 1, current_execution_id, executions, events}`. Initially the ID is null and both arrays are empty. Each execution is separately retained, so an explicit reopen can start a new execution without erasing the previous manager or results. Replacement within an execution increments its generation. Every record below has a stable ID; references must resolve within the same Task and execution. All arrays and strings retain explicit existing size limits; exhaustion blocks rather than truncates history.

The following key sets are exact recommendations. `ref` means a registered immutable artifact ID. `Actor` is `{native_id, assignment_id}`; the assignment is null only for a bootstrap actor proven by a native receipt. `Binding` means `{execution_id, generation, subtask_id, baseline_id, round_id}` and is required on every subtask result. Helper-derived values are never trusted merely because they appear in a payload.

Nullable values represent inapplicable fields, never missing proof for a required gate. Bootstrap/context evidence permits a null producer and null subtask, baseline and round binding; helper fills its execution/generation at reservation. `criterion_evidence` retains the existing exact `{criterion, evidence}` coverage check, with evidence also resolving to registered current artifacts. Blockers and observations must be typed records, respectively `{blocker_id, reason, affected_ids, evidence_refs, next_action}` and `{observation_id, native_id, native_status, tool_receipt_ref, known_changes_ref}`. A synthesis disposition artifact lists `{difference_id, type, candidate_refs, requirement_ids, claims, evidence_refs, outcome, rationale}`; types are the five named difference classes in REQ-026. Structural validation does not replace the manager's inspection of actual semantic coherence.

`stage` for an execution is `reserved | receipt_recorded | active | stopping | stopped | blocked | finished`. Assignment state is `reserved | launch_uncertain | active | stop_requested | stopped | completed | failed | revoked`; “unavailable” is an observation that leaves ownership unresolved. Logical slots with no reservation are queued, avoiding a second scheduler or ledger. Subtask stage is derived from its current baseline, round and accepted records, not freely set by a caller.

Each settings artifact must distinguish `observed_equal`, `verified_inheritance`, and `unverified`, identify the native/configuration evidence, and reject the last state before dispatch. Context independence has its own artifact and gate. Each native receipt records the actual tool name/result, returned native ID, parent scope, and assignment reservation; child success prose cannot replace it. A role-read receipt binds the worker's loaded pair and baseline before accepting its result.

## Typed event and mutation boundaries

Use one envelope: `{event_id, actor, execution_id, generation, kind, data, artifact_imports, response}` with the CLI's existing expected revision. `response` is the existing strict concise response payload. `artifact_imports` is an array of `{artifact_id, source_path, producer_assignment_id, binding, input_refs}`, empty when unnecessary. The helper confines the source, derives the unique destination/digest/byte count, and publishes imports with this event's transaction. References may resolve to same-event imports, which lets the first manager reservation include its inspected evidence without a circular registration prerequisite. Store each accepted event with helper-generated timestamp, response ID, revision before/after and payload digest. Repeated event IDs return an already-applied diagnostic only for the identical payload; conflicting reuse fails. No event is applied again.

| --- | --- |

| `execution.finish` | `verification, outcome`; outcome is `delivered`, `stopped`, or `cancelled`. Only `delivered` with all current criteria and integration evidence can permit Task completion. |

All ordinary schema-2 state writes, including `status_after` on other commands, must pass the same locked writer/generation check. Description or definition-of-done changes require a new Task baseline and affected-subtask invalidation; cosmetic name changes do not. `complete` also requires delivered execution evidence; pause/cancel/age closure cannot claim a final stopped state with unresolved owners. A generation change rejects every delayed old-generation result before mutation.

Projection rebuild remains explicit maintenance: require the current writer for a selected execution, or an explicit bounded recovery authority, and only render validated current state under the existing lock order. Global rebuild may regenerate navigation but cannot assume one manager owns every Task. Redaction retains its existing user authorization and exact correction semantics, plus schema-2 writer/recovery checks. Lock removal keeps its exact owner and explicit authorization checks. These are not ordinary child routes.

For schema-2 response/upgrade intents, retain the current response transaction and add exact `pre_state_sha256, post_state_sha256, event_id, event_payload_sha256, actor, execution_id, generation, artifact_manifest`. Validate the intent's version-specific key set and planned state before canonicalization. Recovery must match the exact pre- or post-state and recorded publications, not just the revision. Complete the frozen transaction without revalidating it as a new post-handoff event. Never respawn, reapply an event, or discard committed work because a projection failed. Legacy intents retain a separate compatible parser.

An explicit legacy upgrade previews Task ID, revision and raw digest, retains the original bytes, and appends the change through this transaction. Preserve prior response bytes, identity, lifecycle meaning and installed-only age semantics. The new orchestration value remains unassigned; do not derive native identities from history. Reads do not upgrade, repair or touch projections. Original bytes are a recovery artifact, not another ledger.
