# Root and initializer collaboration enablement

Authority: the user's current request to enable collaboration in the depot root,
retain it in the Template and enable it automatically when initializing new or
selected existing Sys4AI projects. "Cisco AI" is interpreted as Sys4AI from context.

This is a separate project-Director workflow; preserve the completed implementation
Task, its managed plan/TRD and native goal. No new Task/goal is inferred.

## Requirements

R1. Root contains the complete reviewed collaborate capability, has compatible
installed Task-owner read interfaces and active default collaboration instructions.
R2. Template distributes complete neutral capability and default instructions;
no populated boards, Task/native bindings, grants, learned records or runtime enter it.
R3. Initializer create and first prepare enable collaboration by default, and a
selected previously initialized project receives missing capability through checked
local adoption without rewriting its base receipt edition or provenance.
R4. Customized/incomplete/incompatible packages remain preserved and are reported
as blockers to enabled readiness. No implicit overwrite or bulk product refresh.
R5. Test actual root preflight and current ledger preservation, confined create,
first prepare, earlier-receipt rerun/idempotence and conflict refusal. Do not claim
new native collaboration pilots from deterministic checks.
R6. Update current project documentation and knowledge through existing owners,
retaining historical release evidence and exact source/installation boundaries.

## Decisions and work

- Preserve root Task helpers and root-specific intake policy. Add one exact reviewed
  legacy-depot owner profile to the collaboration read adapter; dispatch directly
  to existing v1 owner interfaces and keep current profile/version2 protections.
  No validator/schema relaxation and no invented v2 context-read attestation.
- Enablement means complete installed capability, compatible owner and required
  Task collaboration habits, with manager-produced Task policy/grants at execution.
  It does not mean a background service, global board or idle-agent wakeup.
- Evolve initializer via its current source package and existing setup/module receipt
  transaction. Preserve earlier editions; enable only the selected destination.
- Host owns collaboration adapter, exact root adoption, documentation/knowledge and
  final integration. One role-based ordinary implementation child owns initializer
  changes and focused confined checks under the project Director's delegation rule.

## Scope

Reusable changes: SKILLS-depo/collaborate, SKILLS-depo/init-new-project and necessary
source starter instructions/policy. Template updates only through the existing pipeline.
Root adoption: exact collaborate package, selected Task/Agent Task collaboration
instruction additions and current initializer package; preserve root AGENTS/ROLE/SOUL,
all role pairs, existing Task helpers/records, configs, products and registry.
Knowledge changes use separately current owner grants after implementation verification.
No Git publication, dependency/model/service installation or external messages.
