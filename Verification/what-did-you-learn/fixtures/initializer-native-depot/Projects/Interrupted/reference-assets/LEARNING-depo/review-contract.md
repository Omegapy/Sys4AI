# Eight-step learning review

Apply the [policy](policy.md) to one bounded work unit. Enter through the memory
skill's shared `references/automatic-capture.md` for explicit reviews and material
checkpoints. That entry supplies the mode, setting and responsible owner; this
contract supplies judgment. Do not call the entry or the learning skill again
from inside the review. Stop after the warranted review and disposition.

## 1. Establish work and ownership

Identify the explicit real project root, current Director or confirmed manager,
relevant discussion or work unit, applicable governing sources, configuration
and permitted reads and writes. Distinguish manual review, explicit save and
automatic checkpoint. A review request creates neither save authority nor a
Task. For independent children, retain the assigned frozen packet and permitted
sources; report missing or changed input to the owner before substituting it.

## 2. Inspect observation and evidence

State what was expected, what happened and which exact artifact versions
establish that observation. Reopen the sources. Separate observation from its
explanation and mark unsettled meaning. When discussion is the only source,
save concise attributed local evidence only if the current scope allows it.
Retain actual project-relative paths, SHA256 values and supported locators.
A missing source or invented receipt cannot be repaired by confident wording.

## 3. Decide whether the finding is durable

Ask whether this information changes how a future agent should perform similar
work. Include verified methods and successes as well as corrective lessons.
Reject temporary, trivial or unsupported candidates. For unresolved discussion,
return a pending observation with its missing evidence; save a draft only in
permitted output. A valid result is "No durable lesson found" with a concise
reason. Do not manufacture content or retry reflection until a note exists.

## 4. Compare accepted memory and current sources

Use the project's installed memory `search` and `read` operations, retaining
frozen-packet restrictions where assigned. Reinspect governing and source files
directly where needed. Identify duplicates, additional support, contradictions
or a problem already addressed by current instructions. A duplicate can end
the checkpoint without publication. For conflicts, review applicability and
use the supported supersession or retraction operation with current prior
versions. Do not silently overwrite history or add duplicate instruction text.

## 5. Form the bounded lesson and proposed disposition

Use the [body template](assets/lesson-body-template.md) for observation, evidence,
lesson and applicability, limits, disposition, and validation/follow-up.
Construct metadata through the existing memory record contract: `type: lesson`
when appropriate, supported claim level and lifecycle, truthful confidence,
exact sources and null non-Task origins. Accepted decisions, performed work,
verified outcomes and observed failures remain distinct. A causal hypothesis
belongs in limitations and a bounded investigation, never as a verified claim.

Identify contextual recall only, a targeted improvement, or further investigation
before approving the lesson. A targeted proposal names the owning project,
owner, exact artifact, behavior, reason, preservation boundary and observable
check. Unsupported cause or benefit needs an investigation question and a
bounded evidence-gathering step. These body statements do not create new
frontmatter fields or authorize the proposed work.

## 6. Review exact bytes and use the existing memory route

For review-only, capture-off without an explicit save, no lesson, unsupported
evidence or missing grant, return the supported finding and precise limitation
without publication. Children return their proposal in their assigned output;
the owner alone decides active publication. The shared checkpoint coordinates
the actual helper call using its existing publication and evidence contracts.

The owner binds the grant to actual record bytes, operation and configuration
hashes, current evidence, expected prior versions and a fresh observed native
receipt. Automatic capture uses only a semantically fitting supported trigger;
an explicit save uses `publish` or `supersede` without changing the preference.
Do not relabel a correction as an accepted decision or an unverified suspicion
as an observed failure to fit a trigger.

Reuse the same operation identity and exact payload on retry. Reopen its
publication receipt and resulting canonical record before claiming a save;
confirm exact or lexical retrieval. An interrupted call may have committed
some records. Report its exact boundary and use memory-only recovery with a
current grant, never a fresh unrelated operation to hide pending work. Optional
capture failure is separate from accepted work; a required publication remains
unmet. Recovery does not reopen terminal Tasks or replay their events.

## 7. Route the improvement

Confirm the disposition against current sources and the user's current change
authority. For an authorized improvement, use the existing requirements,
planning, implementation and verification workflow. For work outside that
scope, return the concrete proposal. When no change is warranted, state why
contextual recall is sufficient. Follow-up evidence belongs in normal delivery
artifacts; a later material correction to the lesson uses memory lifecycle
operations, not an in-place implementation-progress update.

## 8. Verify relevant later use

Retrieve the accepted lesson before comparable work, reassess its current
sources and applicability, and inspect any adopted artifact at its actual
version. Observe whether the original problem recurs or the method helps under
those conditions. Record the bounded observation and limits. Do not equate a
saved note with an installed change, semantic-index readiness, long-term benefit
or universal reliability. Stop after the current scope and checks are satisfied.
