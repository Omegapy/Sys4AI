# VoiceOver observation method: current capability decision

This is a researched preparation decision, not an observed utterance or an accessibility pass. Root is the host observer. The worker has not operated VoiceOver, read or changed the general clipboard, created a Desktop archive, installed software, or run a custom accessibility client.

The current CUA route remains insufficient for spoken-word evidence: root's two attributed probes established that VoiceOver/scrod actually ran, while CUA did not expose the caption window and getApp timed out. Safari AX labels remain native UI structure, not VoiceOver-produced speech. Repeating that same failed interface is not a new experiment. The available screen-context tool is limited to an active voice chat and cannot be repurposed here; no ordinary audio-recording/transcription or clipboard connector is available in the discovered tool inventory.

Apple's [caption-panel guide](https://support.apple.com/guide/voiceover/unac078/mac) identifies the panel as a display of VoiceOver output. This makes an actually observable caption panel suitable evidence, but does not establish that our current app-scoped capture can reach it. Root's observed inability to capture it remains the relevant capability limit.

Apple's [last-phrase guide for macOS26](https://support.apple.com/en-euro/guide/voiceover/vo2725/10/mac/26) documents VO-Shift-C for placing the last spoken phrase on the clipboard and VO-Z for repeating it. Thus a properly attributed copy would originate from VoiceOver, unlike scraping Safari AX text. It would still be a VoiceOver-produced last-phrase transcript, not an acoustic recording. The same guide describes VO-Shift-Z producing an audio archive with logs on Desktop. That wider write/log scope is unsuitable here and is not proposed.

The copy command is a possible future method, not a currently admitted safe observer. Apple's [NSPasteboard documentation](https://developer.apple.com/documentation/appkit/nspasteboard/) describes a shared, multi-item pasteboard that also participates in Universal Clipboard. A generic `pbpaste` or AppleScript clipboard read could expose unrelated content if copying failed or another producer intervened. No such read has occurred.

A future confined observer would require all of the following before execution:

1. An exact reviewed helper and existing trusted execution interface, restricted to the clean owned Explorer document and one deliberate VoiceOver copy action. Verify the real VoiceOver process and actual focused synthetic control immediately around the action; do not infer the producer from expected wording alone.
2. Preserve every existing pasteboard item's exact type/data representation only in bounded process memory, never in output, files, logs or hashes. Refuse before mutation if lazy/promised data cannot be fully retrieved, data exceeds the agreed bound, or any format cannot be restored. An empty or user-provided disposable clipboard would reduce preservation needs but does not by itself prove provenance.
3. Record only ownership counters and boolean preservation outcomes externally. Apple's [changeCount guidance](https://developer.apple.com/documentation/appkit/nspasteboard/changecount) permits detecting ownership changes. It is not a producer identity or an atomic compare-and-swap; it cannot alone prove that VoiceOver made a particular write. A controlled owner-only observation interval and an independently observed copy action would still be required. Any unaccounted change invalidates the sample.
4. Read only a newly observed, attributed VoiceOver copy. Do not emit earlier clipboard values on failure, unsupported-type errors or unchanged counters. Record the exact copied phrase and native action as a distinct evidence method; do not turn generated expectations or matching Safari labels into the phrase.
5. Restore original data only while the helper still owns the value it captured. Preserve any subsequent user/app copy instead of overwriting it; record the interruption and incomplete restoration. Because the public counter is not atomic, a general shared clipboard cannot be represented as race-free. No existing capture helper in this task has established these conditions, so clipboard execution is not released.

Apple also documents a [process-scoped accessibility object](https://developer.apple.com/documentation/applicationservices/1459374-axuielementcreateapplication) and [attribute reads](https://developer.apple.com/documentation/applicationservices/1462085-axuielementcopyattributevalue). These are generic interfaces, not a documented VoiceOver-caption endpoint; unsupported/no-value/cannot-complete outcomes are possible. A custom client would need its own trusted-interface and exact caption/provenance validation. This research does not establish a callable caption API or authorize a new trust grant/system-app change.

The presently concrete path is a real person's contemporaneous report of the words heard from the owned test session, recorded through `voiceover-utterance-checklist.md`, or a later specifically reviewed observer meeting the conditions above. Approval, a running process, screenshots of ordinary Safari, and AX names do not supply an utterance. The independent native keyboard follow-up can proceed while this speech-evidence need remains open. TASK022 and its later dependencies remain incomplete until the actual required evidence exists.
