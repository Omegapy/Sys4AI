# CUA-only synthetic Safari handoff: feasibility assessment

This is a preparation assessment, not a frozen design, execution release or demonstrated safe handoff. NativeTheme01 remains unexecuted and unchanged because its direct osascript launch/poll route does not satisfy the current CUA-only native-method boundary. No replacement listener has been implemented or started.

A separate one-use loopback handoff can mechanically transfer Safari from a non-secret `http://127.0.0.1:<port>/start` navigation to the existing private production bootstrap URL without placing that bootstrap in a CUA argument. A302 response would carry the private Location in process/browser memory. The unchanged production page would then perform its real fragment capture, session exchange, cookie/CSRF handling and authenticated context read. It would not require a new production route or a fabricated session.

## Necessary constraints for a reviewed implementation

- Run only against one fresh explicitly synthetic `explorer-native-at` fixture and its admitted current product bundle. Never target the live depot, an existing session or a user project. Keep all listener state and receipts in the owned disposable stage/runtime.
- Bind an ephemeral IPv4 loopback port with a fixed exact `/start` path. Require one exact Host, GET, no query, no body, no duplicate headers, no transfer encoding/Expect, and bounded request/header bytes/count and absolute read/write deadlines. Reject every other request with a constant small safe response. Do not log request lines, arbitrary header values, URLs, Location, cookies or exceptions.
- Require top-level navigation Fetch Metadata: `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`, `Sec-Fetch-Site: none`, and user activation if the actual Safari navigation supplies it. Reject unsupported metadata rather than silently loosening this admission. Actual Safari metadata compatibility has not been observed; record only allowlisted metadata enums and presence/absence, not raw requests.
- Capture only the exact service-owned bootstrap file through stable no-follow, regular single-link0600 admission with an8192-byte cap; validate exact service origin and token-shaped fragment in memory. No caller-selected file/path, destination or redirect query is accepted. Never print the captured URL or place it in arguments/files beyond the existing private service file.
- Permit one successful handoff, consume it before sending the redirect and immediately close the handoff listener afterward. Use `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, a fixed empty body and connection close. Keep the separate handoff lifetime below the real60-second bootstrap lifetime; do not issue replacement bootstraps automatically. On an incomplete transfer, stop and retain the failed outcome rather than retrying.
- Root uses CUA to create/select the exact owned Safari document and navigate the tokenless address. No AppleScript, browser scripting permission, clipboard or OS setting change is involved. Root preserves unrelated tabs/windows and supplies actual closure/restoration evidence. The service/handoff driver can prove listener/read-worker cleanup, but cannot independently prove that Safari's document was closed under a CUA-only route.

## Authentication and fragment evidence are different

Current `src/api.ts:13–26` calls `history.replaceState` synchronously inside `captureFragment`; the captured result enters the real `connect` path, which exchanges the bootstrap and only then requests authenticated context (`src/api.ts:128–150`). This source order, current compiled-byte identity and a successful authenticated context response support a causal inference that the shipped page cleared the fragment before its own session request. They are not a direct new observation of Safari's address bar, and an authenticated context request alone does not identify which client sent it.

The driver should emit an `authenticated_context_observed` event with current build/fixture/origin only, explicitly labeling this source-based inference. It must not emit `fragment_removed: true` or claim native readiness from HTTP alone. Root must separately verify the exact owned Safari clean route and visible connected synthetic context before content screenshots or interaction evidence. If the UI tooling cannot perform that check without potentially recording a private fragment, that observation capability remains a blocker; no guessed readiness is permitted.

## Security limit that requires review

Fetch Metadata is a browser request guard, not authentication against another local process. A different local process can spoof those headers and race the tokenless endpoint; another OS user with loopback access may have been unable to read the0600 bootstrap file directly. One-use behavior, a short lifetime and synthetic-only data limit exposure but do not preserve the private-file boundary against that race. Such a handoff cannot be described as equivalent to the production private launch mechanism or as new passing security evidence.

Consequently, a reviewed test-only exception would have to accept that narrowly scoped synthetic-session race explicitly, or supply an independently enforceable client-identity mechanism. No such mechanism is currently established. A successful root-observed Safari connection could establish the intended run after the fact; it would not prove the endpoint excluded other local clients. The design should fail the run on unexpected consumption/connection and preserve the failed evidence.

Before freeze/release, manager/root must settle the synthetic-only race boundary, actual Safari navigation metadata admission and safe clean-route observation. Then a bounded harness can be prepared with deny/replay/deadline/cleanup checks and constant secret-safe diagnostics for review. No current code, native probe, speech observation, later qualification gate or product change is authorized by this assessment.
