# Prepared measurement protocol

No measurements have run under this protocol yet. Execute only after TASK021 and TASK023, using the admitted current bundle, in isolation from other owned browser/scanner/build jobs. Record actual hardware, OS, Python and browser versions; normal unrelated host load cannot be assumed absent. Do not change product or shared limits.

Use the complete existing pathological synthetic recipes: approximately 50 entries/100 relationships, 1,000/5,000 and 5,000/50,000, including their imported core, source tuples, long labels/definitions, duplicates, aliases, multiple predicates, cycles, self-loops and high-degree hub. Keep fixture generation outside measured service processes. Retain exact actual counts and byte sizes; predicted admission does not establish capacity. Cold means fresh reader/process state; OS filesystem caches are not flushed and are not claimed cold. No cache-dropping operation is used. Each measurement process starts fresh to avoid fixture-generation RSS contaminating the service parent's 64 MiB budget.

For every full recipe, measure three independent canonical loader runs and three independent dedicated-service startup/first-context attempts. Record each actual successful result or safe refusal, elapsed time, peak observed parent/worker RSS, sampling interval, effective limits and reaping. The canonical loader is separately supervised with a finite wall deadline and memory ceiling; its timings do not substitute for Explorer service results. For any admitted recipe, perform twenty sequential warm HTTP observations of search, entry header/definition and focused neighborhood reads. Preserve individual samples, median and nearest-rank p95 (`sorted_samples[ceil(.95*n)-1]`), sample size and maximum. A refusal is not assigned a made-up completion latency or counted as a success.

Measure the first observed Explorer snapshot/service admission boundary by narrowing the complete small recipe's relationship count between a supported and refused shape, then explicitly test both adjacent shapes. Record the actual condition and all other fixture counts. Report this as the boundary along that particular recipe axis, not a universal capacity. If a different limit or deadline is reached before the source-reference boundary, preserve it. Never increase shared caps to force admission. Distinguish canonical loader capacity from the stricter Explorer snapshot/service boundary. Separately generate two complete small fixtures whose first selected canonical JSON document is padded only with insignificant whitespace to exactly 2,000,000 and 2,000,001 bytes. Verify identical parsed JSON values and preserved record/source counts. The actual unchanged canonical loader must pass the first and refuse the second with `input_too_large` for that exact selected path. This is a per-document byte boundary, not a universal record-count capacity. Full recipe repeats remain separate; bulk shapes that load establish only supported tested points.

Only for complete shapes admitted in all three Service attempts, run five independent production browser cold-read trials, then twenty warm search and entry navigations, five focused Map trials and twenty loaded-graph selections. Report package/service startup, browser startup, navigation-to-readable and controller-child spawn-to-first-readable boundaries separately. The child-spawn boundary includes Python imports, input/runtime verification and inventory overhead; the package-start boundary excludes those earlier steps. Neither is a measurement of public CLI command parsing or user browser-launch integration. The 2-second proposed comparison uses the broader child-spawn observation, with this qualification. Explicit Search submission excludes the intentional 175 ms suggestion debounce. Record automation/observation overhead rather than treating it as pure render CPU time. Map requests use the existing approximately 25-node/50-edge budget; retain actual returned counts, response bytes and incomplete markers. Loaded selection must retain the same renderer and graph member data; do not include a full graph rebuild under that label. Selection feedback timing ends when its selected class updates, and the exact chosen identity and full Definition section must finish before the next sample. Entry samples require the correct identity, active Definition tab, complete expected fixture text, settled requests and unchanged snapshot. Map samples require no retained model, a fresh exact focus and snapshot, the actual 25/50 request, and recorded returned counts/bytes/coverage. Five Map and cold observations retain n=5: nearest-rank p95 equals the maximum and has limited tail inference. This is deliberately distinct from twenty search/entry/selection observations.

The proposed targets remain comparisons, not promises: approximately 2 s cold first readable screen; warm search p95 200 ms excluding debounce; bounded entry p95 250 ms; approximately 1.5 s focused 25/50 graph; and 100 ms loaded selection feedback. Preserve every observed miss. If representative or stress startup refuses the complete recipe, report browser measures as unavailable for that shape with the exact refusal evidence, not as zero or as a smaller substitute dataset.

Exercise actual long-definition and many-source paging, high-degree continuation and cancellation. Observe existing view retention and visible pending feedback while one real owned response is delayed; cancel through actual navigation and release the late response to verify it cannot replace the new view. Mark this fault injection separately from uninstrumented timing samples.

Profile source capture/validation separately on an admitted immutable snapshot. Observe cold materialization and repeated warm reads, exact `_capture`, `_file` and `_materialize` call durations/counts, and whether the same immutable snapshot object is reused after full input validation. Profiling overhead is excluded from production timing claims. If source validation dominates, report current validated reuse before considering any contract change. Do not modify timestamps, fake freshness, bypass validation or treat stale bytes as current.

Compute raw, gzip and Brotli sizes for all five actual runtime assets, with compressor settings and separate vendor totals. These are a regression baseline; they do not imply over-the-wire compression by the local server. Keep individual observations and exact current source/runtime/tool identities, preserve failures, and reap every owned process.

The single future controller integrates canonical/Service recipes, both distinct capacity axes, every admitted shape's browser trials and source-cost profile, and compression. Its finite maximum is 76 cases: 21 full-recipe cases, 4 canonical byte-boundary cases, up to 32 service relationship-axis generation/probe cases, 3 profiles, 15 browser trials, and 1 compression process. Case deadlines sum to at most 8,520 seconds; 988 seconds covers bounded termination/reaping and 600 seconds provides inventory/version/runtime-verification allowance. The outer descriptor permits 10,800 seconds. Exhaustion means an incomplete failed run, never fewer recipes or repetitions. Production 5-second/256-MiB worker/64-MiB parent caps stay unchanged; 512-MiB nonbrowser and 1,024-MiB browser individual-process supervision are test-harness ceilings only.

The controller independently compares every fixture's regular-file bytes, timestamps and modes after all child outcomes, including a killed child or malformed/failed result. Only exact newly created 0700 `.sys4ai`, `.sys4ai/ontology`, and `.sys4ai/ontology/explorer` directories may appear; no regular-file exception exists. Actual parsed safe partial reports survive an interrupted run as separately hashed evidence. Raw invalid stdout and stderr are never emitted. All observed owned descendants must be reaped; emergency descendant cleanup is recorded and fails the case.

Preparation verification is limited to syntax/static checks and deterministic synthetic result-accounting checks. Those checks are not benchmark observations, compressed-size measurements or AT-36 evidence. The frozen job must not execute until original TASK-023 completion and manager/root release.
