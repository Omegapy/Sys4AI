# Authority contract

The effective authority for an operation predates the candidate. An explicitly
accepted standing entitlement allows matching work without repetitive human
approval. Each mutation also requires a fresh exact-operation grant checked by
the trusted broker and the canonical owner. Role prose, a configuration edit,
an offered Task, passing tests and a candidate policy patch grant no authority.

A grant binds the trusted issuer, actual native caller, controller origin,
selected charter, project and repository identity, canonical coordination root,
branch, policy edition/hash, source snapshot/hashes, exact payload digest,
operation class, bounded read/write paths, tools, budget, owner Task/execution/
generation, current writer and expiration. The broker obtains identity from the
trusted request envelope and current manager binding, never an actor string in
model arguments. An operation or grant ID does not authenticate its caller.

Grant validation rejects missing, unknown-version, stale, expired, reused,
out-of-scope or altered grants, mismatched policy/source/payload, uncertain
ownership, unresolved recovery and unsupported confinement. Historical grant
versions retain strict existing semantics; new native observations require
explicit version dispatch. A Curator manager is never relabeled as Director.

| Permission | Independent selection and denial rule |
| --- | --- |
| Bounded analysis/model use | Explicit requested scope or selected automatic budget; idle preflight cannot invoke a model |
| Data/documentation maintenance | Only supported canonical data, factual prose and selected derived maintenance; deny code, schema, validator, instruction and policy changes |
| Technical maintenance | Selected non-governance code/dependency classes, paths, tools and regression obligations; deny speculative refactoring and unselected classes |
| Protected governance change | Prior protected-change grant and independent verification; deny self-approval, authority expansion or weakening its current enforcement |
| Filesystem read | Explicit candidate source roots; deny private grants, credentials, broker code and unrelated projects |
| Candidate filesystem write | Exact isolated workspace paths; deny canonical ledgers and trusted storage |
| Canonical publication | Existing owner's exact grant, current manager and current payload; proposals confer no publication right |
| Capability adoption/installation | Exact source, destination, package and preservation boundary; installs no runtime or service |
| Package-source access | Selected trusted dependency sources; deny undeclared new sources |
| Runtime package/model installation | Exact disposable or selected environment and dependency scope; deny changes to live environments without that selection |
| Network and external tools | Each allowed destination/tool independently selected; filesystem confinement does not authorize network or tool use |
| Host service/hook installation | Exact checkout and existing-hook preservation; source distribution installs none |
| Commit | Selected repository, branch and exact manifest; separate from local file integration |
| Local integration | Serialized exact source/target revalidation and owner checks; preserves staged and later edits |
| Push | Exact selected remote/branch action; a local commit grants no push |
| Merge | Exact selected integration target; a push grants no merge |
| Destructive action | Explicit exact operation and recoverability boundary; no automatic stash, reset, clean or blind rollback |
| Cross-project change | Independently selected project and scope; registration grants no adoption authority |
| External notification | Selected destination and message authority; neutral starters have none |

Mixed or unknown file classes use the stricter applicable boundary or hold for
the missing classification. A rejected data proposal remains rejected; it cannot
repair rejection by editing validators or the protected ownership map. Generated
outputs use their generators; historical evidence retains its temporal meaning.

The broker dispatches only narrowly typed owner operations using frozen trusted
code outside candidate writable paths. It exposes no arbitrary shell, import,
process launcher or protocol proxy. Unrestricted App Server `process/spawn` and
`thread/shellCommand` are denied. Scope and path resolution are checked again
immediately before publication; aliases cannot widen a grant.

Governance changes preserve the policy that evaluates the present operation.
Accepted changes reconcile affected actors, receive separately authorized
binding updates and become effective at a new execution boundary. Broker or
enforcement upgrades occur out of band under separate authority. Old grants
remain rejected under changed bindings. Pause prevents new dispatch, requests
real interruption, reconciles uncertain writers and revokes future grants by
their owners; elapsed time alone never establishes stopping or takeover.
