# Curator ontology integration contract

Edition `curator-ontology-1.0.0` describes the project-local Curator process and
fourteen public functions. The neutral recipe contains no project identity,
Task, native actor, receipt, grant or active session. The initializer specializes
it after final identity, governing sources, owner packages and role index bytes.

The ontology owner renders three reserved files: project/curator.jsonld,
bindings/curator.jsonld and project/curator-competency.json under ONTOLOGY. Its
`integrate-curator` schema-1 operation adds only their exact ontology.yaml
selections and the required source allowlist entries. Existing order, identity,
module/context locks, retrieval, profiles and publication values are preserved.
Canonical IDs use `urn:sys4ai:ontology:project:<id>:curator-` suffixes. The process
and functions are Capability instances, installed contracts are Skill instances,
and persisted supporting roles are Role instances with exact paired provenance.
Public owner skills remain distinct from support roles and current publishers.

The fourteen functions are status, validate, review, update, correct, retry,
pause, resume, tick, session-catch-up, log-register, log-list, log-summary and
log-query. Each has typed input/output, maintenance scope, owner, trigger and
prerequisite edges and current local source bindings. Update/correct/retry link
to their actual integration, memory, ontology and derived-product owner routes.
The process links explicitly to the selected project. Every function has an
observable competency question. Queries distinguish declared source freshness
from installation, configuration, current authorization and observed execution.
They are read-only and retain stale/missing-source and truncation diagnostics.

For authored ontology, public `integration_preview`, `integration_publish` and
`integration_recover` use the separate exact integration grant. It binds the
original configuration predecessor, four exact pre/post targets, recipe/source
inventories, helpers, preview, current native observation, expiry and current
Director or confirmed manager. The three canonical targets must remain within
existing authority scope. Only this named operation may add config selections;
ordinary publication and grant contracts retain their earlier scope. Enabled
guards evaluate its exact request and cannot supply publication authority.
Schema-1 manager grants require orchestration version 1; unsupported protected
native contracts remain explicit holds.

All preimages and immutable intent are persisted before graph, bindings,
competencies and config are replaced in that order. Compile precedes the owner
completion receipt. Cross-file atomicity is not claimed. Recovery recognizes
only original pre/post target bytes with unchanged protected inputs and helpers,
and requires renewed current authority for the original preview. Third-state
edits refuse replay. Existing source bindings to a changed target must already
match its postimage or publication holds before writing. Repeated completed
recovery checks current bytes and never overwrites later edits.

New/pristine setup generates the records under its existing setup transaction
and records separate generated provenance. It grants no live publication.
Compatible authored setup links the exact immutable ontology-owner receipt;
missing authority produces a resumable hold. Earlier setup receipts keep their
v1-v11 editions and opt-outs. Explicit `--adopt-module curator` selects first
adoption; `--refresh-module curator` selects a current refresh. The
`project-curator` alias is equivalent. Refresh ownership comes from exact
completed integration publication or supported completed setup provenance;
equal unowned bytes, partial receipts and malformed proof never grant ownership.
A missing ontology may be installed as a recorded neutral setup prerequisite.
Custom/incomplete packages and incompatible role layouts remain preserved holds.

Lock order is Template shared read, destination setup, ontology publication.
The Template lock is released before registry mutation. Ontology publication
never acquires a setup or Template lock. Static success requires complete
resource closure, identity, selected graph, functions, edges, bindings and current
source digests; it certifies no runtime execution. Session-off and capture-off
remain preserved. Publication-off blocks authored writes while compatible reads
remain available. No scheduler, unattended AI, external action, dependency
installation or unselected-project adoption follows from this integration.
